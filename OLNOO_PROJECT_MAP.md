## OLNOO Main (public site)

- domain: `olnoo.com`
- repo: `RomanVaskin/olnoo`
- production path: `/opt/olnoo/projects/olnoo`
- systemd service: `olnoo-web.service`
- port: `3130`
- env: `/opt/olnoo/projects/olnoo/.env.local`
- technology: Next.js 16.3.3

Responsibilities: public pages, SEO landing pages, contact form. The contact form writes new leads directly into the shared Postgres CRM (server-side, via `DATABASE_URL`, project `olnoo`) — no HTTP hop to `olnoo-admin` for lead creation.

`/admin/crm` and `/admin/social` (and all subpaths) redirect to `https://admin.olnoo.com/en?screen=crm-leads&project=olnoo` and `https://admin.olnoo.com/en?screen=social-posts&project=olnoo`. The legacy SQLite-backed CRM/Social UI (`app/admin/crm/*`, `app/admin/social/*`) and Admin API (`/api/admin/leads/*`, `/api/admin/social/*`) have been removed from this repo, along with `lib/leads.ts`, `lib/social-posts.ts`, `lib/social-types.ts`, and the `better-sqlite3` dependency — this repo no longer reads or writes SQLite. See `Legacy` below.

## OLNOO Admin

- domain: `admin.olnoo.com`
- repo: `RomanVaskin/olnoo-admin`
- production path: `/opt/olnoo/projects/olnoo-admin`
- systemd service: `olnoo-admin.service`
- port: `3140`
- env: `/opt/olnoo/projects/olnoo-admin/.env.local`
- technology: Next.js 16.3.3

`admin.olnoo.com` is the single shared Admin for all OLNOO projects — `olnoo.com` has no operational CRM/Social UI or API of its own anymore (see `OLNOO Main` above).

Unified admin panel. Screens read `?project=<slug>` from the URL.
CRM Overview: `/en?screen=crm-overview&project=<slug>`. CRM Leads: `/en?screen=crm-leads&project=<slug>`. Current production example: `project=olnoo`.

No authentication layer exists on this app yet (no login, no session, no middleware) — every route, including CRM writes, is reachable by anyone who can reach the domain. This is a known, pre-existing gap, not something to silently patch as a side effect of an unrelated task.

### Access to admin.olnoo.com

- **Application level:** `olnoo-admin` has no authentication of its own (no login, session, or middleware in this repository).
- **Confirmed fact (external check):** an unauthenticated request to the production endpoint `https://admin.olnoo.com/api/projects` receives HTTP 401.
- **Conclusion:** production `admin.olnoo.com` sits behind an external access layer that answers before the request reaches Next.js.
- The configuration and the specific technology of that external layer were not checked in this repository or by these changes; do not document or assume anything beyond the facts above.

## Project registry

`projects` is the single source of truth for the project list in the whole Admin. Migration `db/migrations/0017_project_registry.sql` (applied manually, additive and idempotent; apply it BEFORE deploying the code that reads it) adds `archived_at TIMESTAMPTZ NULL` (NULL = active) and `locale TEXT NULL`, backfills a missing `slug` from the first label of the domain host when that slug is free, and an index for active rows. Migration `db/migrations/0018_technical_seo_closed_loop.sql` (manual, additive, idempotent; apply it BEFORE merging/deploying the code that reads it — the registry SELECT names `repository`) adds `repository TEXT NULL` (GitHub `owner/repo`, validated, never guessed; editable in Projects; passed into the Technical SEO Fix task), plus `seo_health_last_result JSONB NULL` and `seo_health_checked_at TIMESTAMPTZ NULL` (the last Technical SEO check, overwritten each time, no history; deliberately NOT in the registry SELECT; read/written only via `lib/seo-health-store.ts`). Existing fields are reused: `name`, `slug` (unique, the key other systems address the project by), `domain`, `sitemap_url`, `status`, `client_id` (required by the schema).

- **One reader:** `listProjects(db, { archived })` in `lib/projects-registry.ts` behind `GET /api/projects` — active projects by default; archived only on an explicit `?archived=include|only`. Technical SEO «Check all» (`/api/seo-health`) calls `listProjects` too (no own SQL, no allowlist). Client side: `useProjects()` (`components/sections/seo-project-picker.tsx`) and the global `ProjectSelector` read the same endpoint. **Screens on the registry:** SEO Overview, Admin Overview, SEO Pages / Keywords / Map / Wordstat / Cleanup / Clusters selectors, Technical SEO, Projects, Clients (project counts), and the global project selector used by Admin Overview, CRM (Overview, Leads), Ads and Social (their `project` slug comes from it). Removed: the hardcoded `projects` array of `lib/data.ts` (it was why DriveSet was missing in SEO Overview / the global selector) and the numbers derived from it. A new active project appears everywhere without a code change.
- **Writes (Projects screen):** `POST /api/projects` (`name`, `domain` required; `slug` defaults to the name, `sitemapUrl` defaults to `<domain>/sitemap.xml`, optional `locale`, `clientId`), `PATCH /api/projects/[id]` (edit `name`, `domain`, `sitemapUrl`, `locale`; `archived: true|false` archives / restores). 409 on a duplicate domain/slug. **The slug cannot be changed** after creation. Without `clientId` the project gets the client of the same name (found or created) — the existing convention; no users/auth/roles. **No hard delete** (no DELETE route, no UI): archiving only sets `archived_at`; all data is kept; archived projects drop out of selectors, overviews and «Check all», and can be restored.
- **Not part of the registry:** per-project integration config keyed by slug stays in code (`UNIFIED_PROJECTS` campaign id, `METRIKA_PROJECTS` counter id, `TRAFFIC_CLASS_PROJECTS` env names) — it describes how a project is wired to Direct/Metrika/CRM, not which projects exist. API routes that take a slug (CRM, Ads, Social) still resolve archived projects by slug; they are only hidden from the selectors. The mock `clients`/`pages`/`keywords`/`clusters`/`leads` sample data in `lib/data.ts` (coverage and CRM sample figures on the overviews) is unchanged.

## CRM

Source of truth: Postgres (same database used by `olnoo-admin`).

Tables: `clients`, `projects`, `leads`.
Relationship: `leads.project_id → projects.id`.
Project resolution: `projects.slug` (e.g. `olnoo`, `insurance`, `aura`, `marketing`).

`olnoo.com`'s contact form now sends leads via `POST /api/leads/inbound` (below) — it no longer writes directly into Postgres (the old `lib/crm-db.ts` direct-insert helper in the `olnoo` repo was removed once DriveSet/CleanTrack/DomTrack/OLNOO were all unified onto the same inbound intake path).

Confirmed API routes (`olnoo-admin`):
- `GET/POST /api/leads` — list (filtered by `?project=<slug>`) and create; used by the Admin UI itself. **`project` scoping (Patch B, fixed fail-open):** missing or `project=all` → every project's leads; a slug that resolves to a real `projects.id` → scoped to that one project; an **unrecognized/typo'd slug → `[]`, never every project's leads**. Previously an unknown slug fell through to "all" (`resolveProjectId` returns `null` for both "all" and "unknown", and the query treated any `null` as "no filter") — a real fail-open bug, now fixed. The scoping decision is a pure function, `resolveLeadsProjectFilter`/`wantsAllProjects` in `lib/leads-project-filter.ts` (unit-tested in `lib/leads-project-filter.test.ts`, no DB needed), kept separate from the route so it's testable under this project's `node --test` convention (route handlers under `app/` aren't directly tested here — see "Telegram Business intake" for why). The `GET` SELECT also now returns `l.contact` (existing column, not previously selected) alongside the existing fields.
- `GET /api/crm/observer/leads?project=<slug>&from=YYYY-MM-DD&to=YYYY-MM-DD` — **CRM Observer, read-only** (see "CRM Observer" below). Unaffected by the `/api/leads` fail-open fix — it already resolves `project` as a single required slug and 404s on unknown (see "Project isolation" under CRM Observer).
- `PATCH/DELETE /api/leads/[id]` — edit and delete.
- `GET /api/projects` (+ `POST`, `PATCH /api/projects/[id]`; see "Project registry"), `GET /api/clients`.
- `POST /api/leads/inbound` — API-key-authenticated (`OLNOO_CRM_API_KEY`) server-to-server intake. **In use by DriveSet, CleanTrack, DomTrack and olnoo.com's contact form** (each sending its own `project` slug) — the single shared ingestion path for every OLNOO-family site.
- `POST /api/telegram/business-webhook` — Telegram Business intake (see "Telegram Business intake" below). Code is in place; **not yet connected to Telegram** (no bot token in production env, no webhook registered).

Migration: `db/migrations/0004_crm_leads.sql` (added `leads` table + `projects.slug`). Applied to production.

CRM rules: Postgres is the only current source of truth for new leads; do not create a second CRM database; `crm-overview` and `crm-leads` read the same data; status/notes persist in Postgres.

### CRM Leads UI (Patch B: Project filter + narrower table)

`screen=crm-leads` (`components/sections/leads-view.tsx`) now takes the same `project`/`onProjectChange` pair as `crm-overview` and `admin-overview`, wired to the URL by `app-shell.tsx` exactly like those two (`ProjectSelector` in the filter bar, value from `?project=`, "All projects" = no `project` param). The filter bar is Project / Search / Status / Source, in that order.

- **Table columns (6, down from 8):** Name, Project, Service, Source, Status, Created. Company, Email and Landing page were dropped from the table — they're unchanged in the lead detail card (`LeadDetail`), which still shows company, email, phone, landing page, referrer, UTM fields, etc. Project shows `project_name` (falls back to `project_slug`), with a `title` tooltip and truncation for long names, same treatment as Name/Service — keeps the table inside ~1280px without horizontal page stretch (`TableShell`'s own `overflow-x-auto` still contains anything narrower viewports can't fit).
- **Search** now matches name, company, email, phone, `contact` and service (previously name/company/email only). `Lead.contact` (UI type, `lib/data.ts`) and `row.contact` (API, `lib/crm-client.ts`'s `fromApiLead`) are new — mapped from the `leads.contact` column that already existed (migration `0010_leads_contact.sql`) but wasn't previously read by `GET /api/leads` or exposed to the UI.
- **Manual lead creation:** the create form (`LeadCreateForm`) now has its own required Project `<select>` (populated from `useProjects()`), independent of the outer filter value once opened. Pre-filled to the filter's project when one is selected; left blank (with a "select a project" hint, submit disabled) when the filter is "All projects". The API already rejected a lead with no resolvable project (`createLeadRecord` → "a known project is required", 400) — this only closes the UI-side gap where the form could previously submit `project: 'all'`.
- **`CrmOverview`'s "Recent leads" table** (`components/sections/crm-overview.tsx`) swaps its Company column for Project (`project_name`/`project_slug`), for the same reason: "All projects" mode previously gave no indication which project a recent lead belonged to.
- **`ProjectSelector`** (`components/project-selector.tsx`, shared by `admin-overview`/`crm-overview`/`crm-leads`) dropdown panel now caps at `max-h-80` with vertical scroll, so a project list of 10+ no longer runs off the bottom of the screen.
- Not changed: Telegram inbound/notifications, CRM Postgres schema/migrations (only an existing column, `contact`, is now selected — no `ALTER TABLE`), SEO, Social, Ads, deploy/nginx/systemd.

### CRM lead-creation notification (Patch C)

`createLeadRecord` (`lib/crm.ts`) now sends the owner exactly one Telegram notification after a **genuinely new** lead is created — never on an idempotent `lead_tracking_id` replay (`InsertLeadResult.replay === true`), and never on a `PATCH`/`DELETE`/status/notes change or any read, since none of those paths call `createLeadRecord`. Gating is the pure `shouldNotifyLeadCreation` in `lib/lead-notify.ts` (same pattern as `lib/leads-project-filter.ts`), unit-tested without a DB.

- **Message:** `formatLeadNotification` (`lib/lead-notify.ts`) — "Новый лид — `<Project name>`", then only the Имя/Услуга/Источник/Контакт lines that actually have a value (Контакт is phone, else email, else `contact`), then a link to the admin CRM Leads screen scoped to `project=<slug>` (`PUBLIC_SITE_URL` + `/en?screen=crm-leads&project=<slug>`; no `lead=<id>` deep link — the UI doesn't support one). The Project name/slug come from a real `SELECT name, slug FROM projects WHERE id = $1` on `lead.project_id` (`resolveProjectInfo`), never inferred from free text — identical for DriveSet, CleanTrack, DomTrack, OLNOO and any future project.
- **Telegram:** reuses `TELEGRAM_BOT_TOKEN` (no new bot/token). One new env var, `CRM_NOTIFY_TELEGRAM_CHAT_ID` — the chat the notification is sent to. Either unset, or the Telegram `sendMessage` call failing (HTTP error or network/exception), never blocks or rolls back the lead save: `notifyLeadCreated` (`lib/lead-notify.ts`) logs (`[lead-notify]`) and returns; `createLeadRecord` also wraps the call so nothing it does can affect the already-saved row.
- **Covered paths (go through `createLeadRecord`):** the Admin UI's manual create form (`POST /api/leads`), the authenticated inbound API (`POST /api/leads/inbound`, in use by DriveSet, CleanTrack, DomTrack and olnoo.com), and (since Patch D) the Telegram Business webhook for @driveset's connection only — every other Telegram Business connection stays `ignored` and never reaches `createLeadRecord`.

### Lead `channel` (distinct from `source`)

`leads.channel` (migration `0020_leads_channel.sql`, nullable `TEXT`, no backfill) answers "how did they get in touch" (`Form`/`Quiz`/`Telegram`/`Email`/`WhatsApp`/`MAX`/`Phone`/...), kept deliberately separate from `source` ("where they came from": `Ads`/`SEO`/`Direct`/`Referral`/...) — `normalizeSource`/`KNOWN_SOURCES` in `lib/crm.ts` are unchanged by this. No enum, no second table: `channel` is plain free text, same pattern as `source` itself.

- **`createLeadRecord`** (`lib/crm.ts`) accepts an optional `channel` on `CreateLeadInput`, stored via `lib/lead-insert.ts`'s `LeadRow.channel` (always named in the `INSERT`, so it's written whenever the column exists — apply the migration before deploying this code, same convention as the other `leads` migrations). Absent/blank `channel` stores `NULL`; nothing is required to change for an existing caller that never sends it.
- **Inbound/manual create:** `POST /api/leads/inbound` and `POST /api/leads` both accept an optional top-level `channel` string and pass it straight through. `GET /api/leads`'s `LEADS_SELECT` now also returns `l.channel`.
- **Notification:** `formatLeadNotification` (`lib/lead-notify.ts`) adds a `Канал: <channel>` line right after `Источник`, only when `channel` is set — the same "only print a line that has a value" rule the rest of the message already follows.
- **Admin UI** (`components/sections/leads-view.tsx`): `LeadDetail` shows a Channel field in the source-information block only when present; the filter bar gained a Channel `<Select>` (client-side, same pattern as the existing Source filter) — filters are now Project / Status / Source / Channel / Search. The main leads table is **not** widened with a new column (kept at 6 columns, same adaptivity rationale as Patch B). `LeadCreateForm` gained an optional Channel `<select>` (blank or one of the known values) — manual leads are never required to set one.
- **Current producers:** olnoo.com's contact form sends `channel: "Form"`; CleanTrack's and DomTrack's Telegram order bots send `channel: "Telegram"`; DriveSet sends `"Quiz"` or `"Form"` depending on which of its own entry points the lead came through (see each repo's own map/architecture doc). `Email`/`WhatsApp`/`MAX`/`Phone` are prepared in the schema/API/UI but have no live integration yet.

## Social

Source of truth: Postgres (`olnoo-admin`), table `social_posts`, `project_id → projects.id`. Live at `?screen=social-posts&project=<slug|all>`.

**Reading Posts/Accounts supports "All projects", the same as CRM Leads and Social Overview; writing (create/edit/publish) always happens in the context of one explicit project, never "all" and never auto-picked.** `project=all` (or no `?project=` at all) lists every project's posts/accounts in one table with a Project column (`listSocialPosts`/`listSocialAccounts` in `lib/social.ts`/`lib/social-accounts.ts`, which join `projects` for the slug/name — same pattern as `LEADS_SELECT` and `lib/social-overview.ts`); picking one project in `ProjectSelector` filters the same table down to just that project's rows. An unresolved/unknown project slug is a `400` error on these two list endpoints (unchanged from before this screen supported "all") — it is never treated as "all". Each row carries its own `project_slug`, and a row's own edit/delete/publish/connection calls are scoped to *that row's* project (`PostDetail`/`AccountDetail` in `social-view.tsx`/`social-accounts-view.tsx` receive the selected row's `projectSlug`, not the screen's current filter) — this matters once the filter is "all" and the table holds rows from several different projects at once. Creating a new post/account (`CreateForm` in both files) requires an explicit project choice: the filter's own project pre-fills the create form only when it is already a real project; "all" leaves the form's own project field blank and the "+ Add" button disabled until the admin picks one — same no-automatic-selection rule `LeadCreateForm` (`leads-view.tsx`) already enforces for CRM.

**Which project a Social screen operates under comes only from the current `?project=` URL param or an explicit click on `ProjectSelector`** (`components/app-shell.tsx`) — never from a project remembered across browser sessions. This was fixed after a production incident: an earlier version of `app-shell.tsx` silently fell back, via `localStorage`, to whatever project the admin had last had selected in an unrelated earlier session whenever `social-posts`/`social-accounts`/`ads` loaded with no `?project=` in the URL — which is how an Instagram account for `@olnooai` and its publications ended up recorded under project `domtrack`'s `project_id` instead of `olnoo`'s, with no visible action by the admin. There is no fallback slug of any kind. (This did not affect VK/Telegram's own per-channel/per-account isolation, which is enforced independently in the database layer — see "VK account connection" and "Telegram channel connection" below; this was specifically about which project's `social_accounts`/`social_posts` rows a screen writes to in the first place.)

Posts and Accounts (`social-view.tsx`/`social-accounts-view.tsx`) each render the same shared `ProjectSelector` every CRM/Admin Overview screen already uses — previously these two screens had no project picker of their own at all; the only way to change which project they operated on was to edit the URL by hand or arrive from another screen that already carried a `?project=` (the localStorage fallback above papered over the common case of landing with none, which is exactly the mechanism that mis-filed the `@olnooai` data). `ProjectSelector` sits in `SectionHeader`'s `action` (top-right, next to the "+ Add" button), the same position `CrmOverview`/`AdminOverview` use — not in the filter row below, so the current project is equally visible and equally reachable on all three Social screens (Overview, Posts, Accounts). Posts/Accounts now render unconditionally regardless of which project is selected, including "all" — there is no longer a blocking "select a project" screen standing in for them (the earlier `SelectProjectPrompt` in `app-shell.tsx` was removed once these two screens gained their own "All projects" read, the same way Social Overview already worked). `ads` is unchanged (still renders nothing with no project, no selector or "all" view of its own) — out of scope for this change; it is the one Social-adjacent screen left requiring an explicit, non-`all` project.

### Social Overview

`?screen=social-overview&project=<slug|all>` (nav: Social → Overview, first item — same position `crm-overview` holds in the CRM group). Read-only, by design: no create/publish action exists on this screen at all; creating a post/account and publishing both still only ever happen on Posts/Accounts, scoped to one explicit project. Mirrors `CrmOverview`'s own shape exactly: `SectionHeader` with `ProjectSelector` in `action`, a 4-metric row, then a two-column section (a recent-items table + a breakdown panel) — same primitives (`SectionHeader`, `Metric`, `TableShell`, `StatusPill`), no new UI components beyond `social-overview.tsx` itself.

`GET /api/social/overview?project=<slug|all>` (`lib/social-overview.ts`'s `getSocialOverview`) is the one new read. It reuses `lib/leads-project-filter.ts`'s `wantsAllProjects`/`resolveLeadsProjectFilter` as-is (not Social-specific despite that file's name) rather than re-deciding project-slug resolution a second time — in particular, **an unresolved/unknown project slug returns `404`/`null`, never silently falls back to "all projects"**, the same fail-closed rule `GET /api/leads` already enforces. This is the only cross-project read in the Social module; no other Social route's behavior changes. No new table, no migration — four plain `COUNT`/`GROUP BY` queries against `social_accounts`/`social_posts`/`social_publications`, each either unscoped (`"all"`) or filtered by one `project_id = $1` (one project), same shape as `LEADS_SELECT` in `app/api/leads/route.ts`.

**The 4 metrics, and why connection errors and publication errors are never combined into one number** (both are literally called "errors" but mean different things — mixing them would misrepresent both):
- **Опубликовано / Published** — `COUNT(*) FROM social_publications WHERE status = 'published'`. Not time-bounded (no period picker exists on this screen yet; a lifetime count is the only thing that's unambiguous without one — see "open question" below).
- **Запланировано / Scheduled** — `COUNT(*) FROM social_posts WHERE status = 'ready' AND publish_date <> ''`. Deliberately *not* re-derived against `isPublishDue` (`lib/social-scheduler-due.ts`): a post whose `publish_date` has already passed but hasn't been swept yet is still "scheduled" from this screen's point of view (waiting on the next sweep), not reclassified as something else depending on the exact moment the page happens to load.
- **Аккаунты / Accounts** — `social_accounts` total count, `GROUP BY status` (`lib/social-overview-metrics.ts`'s `summarizeAccountStatusCounts`). The `error` bucket here is a **lost connection** (the account's own VK/Telegram check failed — see "VK account connection"/"Telegram channel connection" below) and is shown in its own "Статус аккаунтов" panel (same `CrmOverview`-style breakdown as "By source"), never folded into the 4th metric.
- **Ошибки публикаций / Publication errors** — a separate `COUNT(*) FROM social_publications WHERE status = 'failed'`: one specific post failed to publish on one specific platform. A completely different query against a different table from the accounts breakdown above; nothing here is ever summed with `accounts.error`.

**Open question / minimal decision taken:** there is no existing, unambiguous definition of "published"/"scheduled" *for a period* (day/week/month) anywhere else in Social — `social_publications`/`social_posts` carry timestamps but no screen has ever needed to bucket them by period before this one. Rather than inventing a period definition no other part of the app uses, this Overview reports lifetime totals (scoped by project, never by time) until a real requirement for a period view exists; adding one later is a filtered `WHERE`, not a schema change.

Recent publications (left column, `LIMIT 10`, `ORDER BY updated_at DESC`) joins `social_publications` → `social_posts` (topic) → `projects` (slug/name for the Project column) — same join shape `LEADS_SELECT` already uses for its own "Project" column. `"all"` shows rows from every project, each labeled with its own project name; a single-project view only ever shows that project's own rows — confirmed isolated in both directions (verified manually against a real Postgres: a second project's rows never leak into a scoped view, and the aggregate view always includes both).

Confirmed API routes (`olnoo-admin`): `GET/POST /api/social` (`GET` filtered by `?project=<slug|all>` — `all`/missing joins every project's posts with `project_slug`/`project_name`, a real slug scopes to one project, an unknown slug is a 400; `POST` always creates under one explicit project slug, never `all`), `GET/PATCH/DELETE /api/social/[id]` (all project-scoped — a post id from another project cannot be read, edited, or deleted by supplying a different project slug or vice versa; unaffected by the "all" list mode above).

**Every post object the client ever receives — from the list (`GET /api/social`), a single fetch (`GET /api/social/[id]`), a create (`POST /api/social`), or an edit (`PATCH /api/social/[id]`) — always carries its own `project_slug`/`project_name`.** `getSocialPost` (`lib/social.ts`) joins `projects`, same as `listSocialPosts`; `createSocialPost`/`updateSocialPost` re-read their row through `getSocialPost` rather than returning the bare `RETURNING *` row, using the project already resolved for that call — no new resolution mechanism. This closed a bug (post-PR #54, when Posts gained its "All projects" list): a freshly created/edited post reached the client with an *empty* project slug, so the next per-post action scoped to its project — in particular Instagram image upload (`POST /api/social/upload-instagram-image?project=`) — sent `project=` (empty) and failed with the API's own raw `"a known project is required"` error. `social-view.tsx`'s upload handler also gained a defensive client-side guard (refuses to call the upload endpoint at all when no real, specific project is known, showing a clear localized message instead) as a second line of defense, consistent with CreateForm already refusing to submit without one.

Post fields (create/edit UI): Topic, Content (shared body), Channels (`telegram`/`instagram`/`threads`/`vk`), Publish date, Status, and an optional per-channel text override per selected channel. `category` is a legacy column still present in the table — no longer shown in create/edit, the Posts list, or search; existing rows keep whatever value they already had, and new rows never get one written. When `instagram` is a selected channel, an "Instagram image" upload control appears — always visible while Instagram is selected, independent of the "Different text per channel" toggle, since it's mandatory content for Instagram publishing (see Instagram autoposting below), not a per-channel text override. It uploads a JPEG (see Instagram image upload below) and auto-saves the resulting URL into `social_posts.instagram_image_url` immediately, without waiting for the post's own Save button.

Per-channel text: every selected channel uses the shared Content by default. The "Different text per channel" toggle (off by default; auto-enabled when opening a post that already has a real override) reveals a text field for each *currently selected* channel when on — an empty field there falls back to Content. Turning the toggle off and saving clears the per-channel overrides for the channels selected at that moment; Content itself is never touched, and a channel's override is left alone while that channel isn't currently selected.

"Generate variants" (post edit UI, shown once Content is non-empty and at least one channel is selected) calls the existing OLNOO AI Router (`lib/ai-router.ts`'s `callAiRouter`, the same client SEO clustering uses — no separate provider integration) via `POST /api/social/generate-variants` (`lib/social-ai.ts`, project-scoped through the same `resolveProjectId`; sends Topic, Content, the selected channels, and project name/domain as context). The output language is always detected from Content itself (`detectContentLanguage` — Cyrillic present means Russian, otherwise English); the UI's interface locale is never sent to this endpoint and never affects the generated language, only the app's own interface strings — a Russian Content on an English-locale screen (or vice versa) still generates in Russian. The AI Router returns JSON with one key per requested channel only — the server drops any other key even if the model returns one — and the client fills the matching per-channel fields, turns the toggle on, and stops: nothing is sent to the server until the user clicks Save. No autoposting; this only asks the Router for text.

Migration: `db/migrations/0005_social_posts.sql`. `instagram_image_url` added by `db/migrations/0008_social_posts_instagram_image.sql`.

Data layer: `lib/social.ts`, reuses `resolveProjectId` from `lib/crm.ts` — no separate project-resolution mechanism.

The old `olnoo` implementation (`app/admin/social/`, `app/api/admin/social/*`, SQLite `social_posts` table in `data/crm.sqlite`) has been removed from the `olnoo` repo; `/admin/social` (and subpaths) now redirect to `admin.olnoo.com`, the same way `/admin/crm` does. ### Social Accounts

Inventory of social accounts, listable per-project or across all of them. Table `social_accounts` (`project_id → projects.id`), `platform` one of `telegram`/`instagram`/`threads`/`vk`, `status` one of `created`/`connected`/`error`. Live at `?screen=social-accounts&project=<slug|all>` (nav: Social → Accounts, alongside Posts).

API routes (`olnoo-admin`): `GET/POST /api/social-accounts` (`GET` filtered by `?project=<slug|all>` — `all`/missing joins every project's accounts with `project_slug`/`project_name`, a real slug scopes to one project, an unknown slug is a 400; `POST` always creates under one explicit project slug, never `all`), `GET/PATCH/DELETE /api/social-accounts/[id]` (project-scoped, same isolation guarantee as `/api/social`), `POST /api/social-accounts/[id]/vk-connection?project=<slug>` (VK only, always one explicit project — see "VK account connection" below), `POST /api/social-accounts/[id]/telegram-connection?project=<slug>` (Telegram only, always one explicit project — see "Telegram channel connection" below), `POST /api/social-accounts/[id]/instagram-connection?project=<slug>` and `POST /api/social-accounts/[id]/threads-connection?project=<slug>` (Instagram/Threads, always one explicit project — see "Instagram/Threads account connection — Social Connect MVP" below).

Data layer: `lib/social-accounts.ts` — reads/writes an explicit column allowlist (`ACCOUNT_COLUMNS`), not `SELECT *`/`RETURNING *`, since every row returned here is serialized straight into a `NextResponse.json(...)` response by the API routes above. This is now load-bearing, not just a safety net: `social_accounts.vk_access_token_encrypted`/`instagram_access_token_encrypted`/`threads_access_token_encrypted` (see "VK account connection" and "Instagram/Threads account connection" below) are real secrets (ciphertext) and are deliberately excluded from `ACCOUNT_COLUMNS` — never selected by the accounts list/detail API, only by the server-only modules that need each one (`lib/social-vk.ts`/`lib/social-accounts-vk-connection.ts`, `lib/social-instagram.ts`/`lib/social-accounts-instagram-connection.ts`, `lib/social-threads.ts`/`lib/social-accounts-threads-connection.ts`). `username` is also load-bearing, not just cosmetic: the Instagram/Threads global-fallback ownership guard (see below) compares it against the actually-connected account before publishing, so it must hold the real `@handle`.

No real OLNOO accounts are seeded by migration — they are added manually via the Accounts UI after deploy.

### VK account connection (per-project credentials)

Each project connects its own VK community from the Accounts UI (Social → Accounts → a `vk`-platform account) by pasting that community's own access token — no OAuth flow, same manual-token convention as Telegram/Instagram/Threads' env-var tokens, just entered per-account instead of once globally. This replaced VK autoposting's previous single global `VK_ACCESS_TOKEN` (see "VK autoposting" below for why and what changed).

- **Storage:** `social_accounts.vk_access_token_encrypted` (TEXT, ciphertext only) — AES-256-GCM via `lib/social-account-crypto.ts` (`encryptAccountSecret`/`decryptAccountSecret`), key from the server-only env var `SOCIAL_ACCOUNT_ENCRYPTION_KEY` (base64, must decode to exactly 32 bytes). Unset/malformed key fails closed — encrypting or decrypting throws rather than ever falling back to plaintext. Migration `db/migrations/0021_social_accounts_vk_credentials.sql` also added `vk_group_id` (the numeric community id resolved from the token — not a secret) and `connection_error` (last verification error, if any — not a secret).
- **Verification (requirement: check through the official VK API):** `lib/social-vk-verify.ts`'s `verifyVkGroupToken` calls VK's `groups.getById` with the token and no `group_id` — VK's own documented behavior for a community/group token is to return that one group's identity; a user token or an invalid/revoked one comes back as a VK API error instead. This is also how a screen name/display name get auto-filled into `username`/`public_url` (only if those were empty — never overwritten) and how `vk_group_id` is resolved, so publishing never has to re-resolve a screen name per post.
- **Connect/recheck endpoint:** `POST /api/social-accounts/[id]/vk-connection?project=<slug>` (`lib/social-accounts-vk-connection.ts`'s `connectOrRecheckVkAccount`, project-scoped). Body `{ accessToken }` connects a new/replacement token; an empty body re-checks the token already stored (the Accounts UI's "Recheck connection" button, requirement 6's "show status + error if access is lost"). The two failure cases are handled differently on purpose: a **replacement** token that fails verification changes nothing in the database (the account's existing working connection, if any, is left exactly as it was — a typo can't knock out a connection that was fine) and the error is returned directly to the caller; a **recheck** of the already-stored token failing means the existing connection has genuinely lost access, so `status='error'` and `connection_error` ARE persisted and shown in the UI. The response never includes `vk_access_token_encrypted`.
- **UI:** the account detail drawer (`components/sections/social-accounts-view.tsx`), for `platform='vk'` accounts only, shows a connection status dot + label, any `connection_error`, a password-style token input (always blank — the token is never sent back from the server, by construction), "Connect"/"Recheck connection" buttons, and an "Open in VK" link using `public_url` once set.

### Instagram/Threads account connection — Social Connect MVP (per-project credentials)

Each project can now connect its **own** Instagram/Threads account from the Accounts UI (Social → Accounts → an `instagram`/`threads`-platform account), the same per-account model VK already has (see "VK account connection" above) — replacing the previous single-tenant shape where every project shared one global `INSTAGRAM_ACCESS_TOKEN`/`THREADS_ACCESS_TOKEN`, gated only by `INSTAGRAM_OWNER_PROJECT`/`THREADS_OWNER_PROJECT` naming the one project allowed to use it. The global env-credential path is **not removed** — it remains a deliberate, explicit fallback (still gated by the same owner-project env var, unchanged) so OLNOO itself never loses the ability to publish while other projects migrate to their own connection; see "Credential resolution order" below.

**What was researched before building this (per this task's own requirement not to assume Meta's rules):**
- Instagram Login issues a long-lived access token (~60 days) for an Instagram **Business or Creator** account (a `PERSONAL` account cannot use the content-publishing endpoints at all). An app whose own accounts are added as Admins/Testers/Developers in the Meta App Dashboard can generate such a token for those accounts directly from the dashboard — no App Review needed. Refresh: `GET https://graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token&access_token=<token>`, eligible once the token is at least 24h old and not yet expired; a successful refresh is valid for another ~60 days.
- Threads has the same shape: a long-lived token (~60 days), refreshed via `GET https://graph.threads.net/v1.0/refresh_access_token?grant_type=th_refresh_token&access_token=<token>`, same 24h-minimum-age/not-yet-expired eligibility.
- **Blocker, explicitly not implemented:** onboarding an arbitrary **third-party client's** account through a one-click "Connect Instagram/Threads" OAuth button (so the client never has to generate/paste a token themselves) requires the app to request `instagram_business_*`/`threads_*` permissions at **Advanced Access**, which needs **Meta App Review + Business Verification**. This MVP only implements the safely-available part: a project admin pastes a long-lived token obtained via the Meta App Dashboard (same manual-token convention VK already uses), and the app verifies it, resolves the real account id, and stores it encrypted. A real OAuth "Connect" button for arbitrary external clients is future work gated on that Meta review, not something this PR can fake readiness for.

- **Storage:** `social_accounts.instagram_access_token_encrypted`/`threads_access_token_encrypted` (TEXT, ciphertext only) — same AES-256-GCM via `lib/social-account-crypto.ts`, same `SOCIAL_ACCOUNT_ENCRYPTION_KEY` env var VK already uses (no new key). Migration `db/migrations/0022_social_accounts_meta_credentials.sql` also added `instagram_account_id`/`threads_user_id` (the numeric id resolved from the token, not a secret) and `instagram_token_expires_at`/`threads_token_expires_at` (TIMESTAMPTZ, not a secret). Reuses the existing generic `status`/`connection_error` columns (added by `0021` for VK).
- **Verification:** `lib/social-instagram-verify.ts`'s `verifyInstagramAccountToken` / `lib/social-threads-verify.ts`'s `verifyThreadsAccountToken` call each platform's documented `/me` endpoint (`fields=user_id,username,account_type` / `fields=id,username`) — this is both the "does this token work" check and the account-id lookup in one call (no numeric id to paste by hand). Instagram additionally rejects a `PERSONAL` `account_type` outright (content publishing requires Business/Creator) — a manually-set `connected` status is never trusted as confirmation; only this real API call is. **`username` is always overwritten with this verified identity** (review fix) — `connectOrRecheckInstagramAccount`/`connectOrRecheckThreadsAccount` never keep a stale/mistyped `username` typed in before a successful connect/recheck confirms a *different* real identity, since this field is what the Accounts UI shows as "which account this is"; the field only ever falls back to the pre-existing value in the (unobserved) case where Meta's own answer carries no username at all.
- **Refresh:** `lib/social-meta-token-refresh.ts`'s `refreshInstagramLongLivedToken`/`refreshThreadsLongLivedToken`, implemented only after confirming each platform's own refresh-eligibility rule above. Refresh is attempted **only on an explicit "Recheck connection"** (never automatically mid-publish, to keep the hot publish path free of extra network calls and side-effecting writes) — `lib/social-accounts-instagram-connection.ts`/`lib/social-accounts-threads-connection.ts`'s `connectOrRecheck*Account` tries a refresh first on a recheck (ineligible/failed refresh falls back to verifying the existing token as-is, never treated as a connection failure by itself) and verifies-only (never refreshes) on a brand-new/replacement token, since a token that was just pasted is always younger than the 24h minimum.
- **Automatic refresh before expiry:** implemented as its own daily sweep, independent of the manual-recheck refresh above — see "Automatic Instagram/Threads token refresh (daily sweep)" below for the full design (deliberately NOT folded into `lib/social-scheduler.ts`'s own once-a-minute publish sweep, and why).
- **Connect/recheck endpoints:** `POST /api/social-accounts/[id]/instagram-connection?project=<slug>` / `.../threads-connection?project=<slug>`, project-scoped, same request/response shape and same two-failure-mode handling as VK's endpoint (a bad replacement token changes nothing in the DB; a failed recheck of the already-stored token persists `status='error'`+`connection_error`). The token itself is never echoed back.
- **Credential resolution order (`lib/social-instagram.ts`/`lib/social-threads.ts`):** for a publication's linked account, (1) if `instagram_access_token_encrypted`/`threads_access_token_encrypted` is set, decrypt and use it with the stored `instagram_account_id`/`threads_user_id` — **no ownership check needed**, since the account row was only ever read `WHERE project_id = $2`, so this credential could never have been resolved for any other project to begin with; an already-expired per-account token blocks publishing with a clear, actionable error (403) rather than being used or silently falling back to the global credentials. (2) Otherwise, the original global-env-fallback path runs exactly as before this MVP: `INSTAGRAM_OWNER_PROJECT`/`THREADS_OWNER_PROJECT` gate, then `compareAccountOwnership` against the global credential's actual handle (see "Instagram autoposting"/"Threads autoposting" below) — unchanged code, just now only reached when the account has no credential of its own.
- **UI:** the account detail drawer, for `platform='instagram'`/`'threads'` accounts, shows the same connection status dot/label/error, a password-style token input with a hint pointing at the Meta App Dashboard and naming the App-Review limitation, and "Connect"/"Recheck connection" buttons — same layout as VK's block.
- **Migration:** `db/migrations/0022_social_accounts_meta_credentials.sql`, additive/idempotent. Not yet applied to production — apply manually (`psql "$DATABASE_URL" -f db/migrations/0022_social_accounts_meta_credentials.sql`), same as every other migration in this repo. No existing project needs to do anything: an account with no per-account token keeps using the global env fallback exactly as it did before this PR.

### Telegram channel connection (per-project channels, one shared bot)

Each project connects its own Telegram **channel** from the Accounts UI (Social → Accounts → a `telegram`-platform account) by entering that channel's `@username` or numeric chat id into the existing `username` field and clicking "Connect" — no new bot, no OAuth, no per-project secret. There was never a global-credential cross-project risk here the way VK/Instagram/Threads had: a Telegram Bot API token is not scoped to one chat the way an Instagram Login token or (until the change above) a VK community token is — a single bot can legitimately be an admin of many different channels, each client's own, with its posting rights to each one managed independently in Telegram itself. So the existing shared `TELEGRAM_BOT_TOKEN` (unchanged, still global, still the only bot) stays exactly as it was; what this adds is **verifying** that the bot actually has posting rights in the specific channel a project names, and a **guard against two projects pointing at the same channel by mistake** — neither of which existed before.

- **Verification (requirement: check the bot can actually publish there):** `lib/social-telegram-verify.ts`'s `verifyTelegramChannelAccess` calls the official Bot API: `getMe` (the bot's own numeric id) → `getChat` (confirms the chat exists and is really a `channel`, not a group or private chat) → `getChatMember(chat_id, bot's id)` (confirms the bot is `creator`, or `administrator` with `can_post_messages` not explicitly `false`). A channel that exists but where the bot was never added, or was added without posting rights, is rejected here with a specific error — rather than only failing at the next actual publish attempt.
- **Connect/recheck endpoint:** `POST /api/social-accounts/[id]/telegram-connection?project=<slug>` (`lib/social-accounts-telegram-connection.ts`'s `connectOrRecheckTelegramAccount`, project-scoped). Body `{ username }` connects a new/replacement channel identifier; an empty body re-checks the channel already stored (the Accounts UI's "Recheck connection" button, requirement 3's "show a real connection status"). Same two failure modes as VK's connection endpoint, on purpose: a **replacement** identifier that fails verification changes nothing in the database (an existing working connection is left exactly as it was); a **recheck** of the already-connected channel failing (bot removed as admin, rights revoked, channel deleted) means access was genuinely lost, so `status='error'` and `connection_error` ARE persisted.
- **Cross-project channel isolation guard, keyed on the confirmed `chat.id`:** before persisting a successful connection, the endpoint refuses (409) if another project's Telegram account already holds the same channel with `status='connected'`. The comparison key is `canonicalChatIdentifier` — the channel's own `username` as returned by `getChat` if it has a public one, else its numeric `chat.id` — never the raw text an admin typed. This matters because `getChat` always resolves to the SAME canonical identity regardless of which form (`@handle` vs the numeric id copied from a forwarded message) was used to query it: without canonicalizing on that, two projects could each "successfully" connect to the identical channel just by naming it differently, and a raw-text comparison would miss the collision entirely. Without the guard at all, the shared-bot design would let two projects' admins each enter the same channel (by mistake, or by copying a config) and both would "successfully" connect to it. This sits at connect time rather than at publish time because, unlike VK/Instagram/Threads, there is no per-project credential for the publisher to be scoped to in the first place — `social_accounts.username` naming the right chat **is** the whole mechanism, so it has to be the thing kept exclusive.
- **Concurrency:** the conflict check and the write are a classic check-then-act, so two simultaneous connect requests for the *same* channel (different accounts/projects) could otherwise both pass the check before either commits. `connectOrRecheckTelegramAccount` wraps just that part — not the slow Telegram API call before it — in one transaction holding a Postgres advisory lock keyed by the canonical channel identifier (`pg_advisory_xact_lock`, auto-released at commit/rollback — same mechanism `lib/social-scheduler.ts` already uses for its own overlap protection, here transaction-scoped and per-channel instead of session-scoped and global). The second request blocks until the first commits, then correctly sees the now-connected row and is refused — verified with two concurrent requests for the same channel named by different identifier forms (`@username` vs numeric `chat.id`), where exactly one succeeded and the other was refused with 409, every time. No unique constraint or migration was needed for this.
- **A plain PATCH cannot forge a connection:** `updateSocialAccount` (`lib/social-accounts.ts`) refuses (400) a `telegram` account's `username` change or a forced `status: 'connected'` outright — both only ever change through the connect endpoint above, which is the only path that calls the Telegram API first. Before this, a direct `PATCH /api/social-accounts/[id]` could silently repoint a `connected` account at a different chat_id (the publisher would then trust an unverified channel), or flip `status` straight to `connected` with no check at all; `createSocialAccount` has the same guard against creating an already-`connected` telegram account. Every other field (name, public_url, notes, active, a non-`connected` status) still PATCHes normally — this is not a lock on the whole account, only on the two fields that assert a verified connection. The Accounts UI's own autosave-on-blur (`saveAll` in `social-accounts-view.tsx`) excludes `username` for `telegram` accounts for the same reason, so editing that field only ever takes effect through the "Connect" button.
- **No schema change:** `username`/`public_url`/`status`/`connection_error` already existed (the latter two added by `db/migrations/0021_social_accounts_vk_credentials.sql` for VK, but deliberately generic columns, not VK-prefixed — reused here as-is). `lib/social-telegram.ts` (the publisher) is unchanged — it already resolved its target `chat_id` from the project-scoped `social_accounts.username`, so connecting a channel through this new endpoint is exactly populating the same field a verified, working value.
- **UI:** the account detail drawer, for `platform='telegram'` accounts only, shows a connection status dot + label, any `connection_error`, "Connect"/"Recheck connection" buttons (using the channel identifier already typed into the Username field), and an "Open in Telegram" link using `public_url` once set (auto-filled from the channel's own `username` on a successful connect, same as VK's auto-fill — only if `public_url` was empty).
- **Manual Telegram-side step (once per channel, outside Admin):** add the existing shared bot to the channel as an administrator with "Post Messages" enabled (Telegram channel → Administrators → Add Administrator → the bot's `@username`) — the same one bot used for every project, no new bot to create. Only after that will "Connect" in Admin succeed.

### Publication tracking

Per-channel publication status for each post, table `social_publications` (`project_id → projects.id`, `social_post_id → social_posts.id` cascade-deleted with the post, `social_account_id → social_accounts.id` set null if the account is deleted, plus `external_url`, `external_post_id`, `published_at`, `error`). `status` one of `draft`/`ready`/`published`/`failed`. One row is auto-created (status `draft`) for each channel as it's selected on the post — always as a side effect of the post's `channels` being written (`updateSocialPost`/`createSocialPost` in `lib/social.ts`), never from reading the Publications list. Channels later deselected keep their existing row rather than being deleted.

API routes (`olnoo-admin`): `GET /api/social-publications?post=<id>&project=<slug>` (pure read — lists whatever publication rows already exist for the post; creates nothing), `PATCH /api/social-publications/[id]` (project-scoped; assigning a `social_account_id` is rejected with 400 if that account doesn't belong to the same project). Setting `status` to `published` sets `published_at` to now (if not already set); setting it to anything else clears `published_at`.

MVP UI: manual "Mark as published" (optionally with an external URL) and "Back to ready" inside the post's Publications block, for any platform that isn't one of Telegram, VK, Instagram, or Threads. Telegram, VK, Instagram, and Threads all have real automated posting (see below).

`social_publications` is the only source of truth for whether a post is actually published — `social_posts.status` cannot manually claim `published`. All the reconciliation and creation logic lives in `lib/social.ts` (`syncPostStatusFromPublications`, `ensurePublicationsForChannels`, `isFullyPublished`) so `lib/social-publications.ts` can import it without a circular dependency; `status` becomes `published` only once every currently selected channel has a `published` publication, and is demoted back to `ready` the moment that stops holding. Read paths are strictly read-only — `listPublicationsForPost` never writes anything, not even to create a missing publication row. Reconciliation runs only after an operation that actually changes state: a publication's status changes (`updateSocialPublication` in `lib/social-publications.ts`), or the post's own selected channels change (`updateSocialPost`/`createSocialPost` in `lib/social.ts`, which is also where missing publication rows get created — always as a side effect of channels being set, never of a read). `updateSocialPost` also rejects `status: 'published'` outright (400) if the resulting channel set isn't actually fully published yet, and `createSocialPost` rejects creating a post already published — the API enforces this, not just the UI's disabled dropdown option. The Post UI computes the same fully/partially-published/ready/draft summary live from `social_publications` (`components/sections/social-publications.tsx`, `summarizePublications`) — nothing new is stored for this, it's derived on every read.

Migration: `db/migrations/0007_social_accounts_publications.sql` (both tables). Applied to production.

### Telegram autoposting

MVP automated posting for Telegram only (VK/Instagram/Threads are untouched — still manual, see above). From the post's Publications block, a `telegram`-platform publication that isn't already `published` shows a "Publish to Telegram" button in place of the manual "Mark as published" button; other channels are unaffected.

`POST /api/social-publications/[id]/publish-telegram?project=<slug>` (`lib/social-telegram.ts`, project-scoped through `resolveProjectId` like every other route in this module) calls the Telegram Bot API's `sendMessage` directly (no separate provider service, unlike the AI Router) using a bot token read from the server-only env var `TELEGRAM_BOT_TOKEN` — never stored in Postgres or Git, never sent to the browser. `TELEGRAM_API_BASE_URL` is a second, non-secret env var (default `https://api.telegram.org`) that only exists so a non-production environment can point at a mock server for testing, the same role `AI_ROUTER_URL` plays for `lib/ai-router.ts`.

Text sent is `social_posts.telegram_text` if non-empty, else `social_posts.body`. The target chat is the `social_accounts` row linked via the publication's `social_account_id` if set (rejected with 400 if that account isn't itself a `telegram` account), else the project's first `active` `telegram` account (`ORDER BY created_at ASC`) — there is no per-post channel picker yet, one active Telegram account per project is assumed. `external_url` is built as `https://t.me/<account.username without a leading "@">/<message_id>`.

No schema change: this reuses `social_publications`' existing `status`/`external_post_id`/`external_url`/`published_at`/`error` columns, all already present in `0007_social_accounts_publications.sql`. On success the row is set to `status='published'`, `external_post_id` = Telegram's `message_id`, `external_url` as above, `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs same as any other publication write. On a Telegram API error (bad request, chat not found, network failure) the row is set to `status='failed'` with the message in `error` — this is not thrown as an HTTP error, the route still returns 200 with the row, so the existing UI's error display (`publication.error`) shows it directly; calling the endpoint again from `failed` is a normal retry (nothing marks it non-retryable). Calling the endpoint on a publication that is already `published` is rejected with 409 before any Telegram API call (duplicate-send protection); calling it on a non-`telegram` publication is rejected with 400. No scheduler or background job exists — this only ever runs synchronously from the button click.

This publisher itself is unchanged by "Telegram channel connection" above — it already read its target chat from the project-scoped `social_accounts.username`, which is exactly the field that endpoint now verifies before saving. Connecting a channel through Admin is what makes that `username` trustworthy (bot verified able to post there) rather than a guess the admin typed in; publishing itself still works exactly as before, including for an account connected the old way (manually typed, never run through "Connect") — this change only adds a way to verify and a way to block an accidental cross-project duplicate, it does not require re-connecting every existing account to keep working.

### VK autoposting

MVP automated posting for VK only, built on the same pattern as Telegram autoposting above (VK/Telegram are now both automated; Instagram/Threads are untouched — still manual). From the post's Publications block, a `vk`-platform publication that isn't already `published` shows a "Publish to VK" button in place of the manual "Mark as published" button; Telegram's flow is unchanged.

`POST /api/social-publications/[id]/publish-vk?project=<slug>` (`lib/social-vk.ts`, project-scoped through `resolveProjectId` like every other route in this module) calls the VK API's `wall.post` (`POST https://api.vk.com/method/wall.post`, `from_group=1` so the post is published as the community, not as the token's own user).

**Credentials are per-project, not global — the root-cause fix for cross-project publish risk.** Earlier, every project shared one global `VK_ACCESS_TOKEN` env var, the same single-tenant shape Instagram/Threads had; a project's `social_accounts` row only proved that project *believed* VK was connected, never that the shared token actually pointed at *that* project's community — the same gap Instagram/Threads closed with an owner-project env var pin. VK's fix goes further: since a VK community token is obtained manually per community anyway (no Login-style single-account constraint forcing one token total), each project now connects and stores its **own** token — see "VK account connection" above. `lib/social-vk.ts` decrypts `social_accounts.vk_access_token_encrypted` from the specific account row the publication is already linked to (project_id-scoped, same as every other query here) and refuses to publish (400) if that account has no token connected yet — there is no shared credential left to fall back to, so a project that hasn't connected its own community simply can't publish, rather than guessing whose credentials to use. `VK_ACCESS_TOKEN` is no longer read anywhere; `VK_API_BASE_URL` (non-secret, default `https://api.vk.com`) is unchanged, same role as `TELEGRAM_API_BASE_URL`/`AI_ROUTER_URL`.

Text sent is `social_posts.vk_text` if non-empty, else `social_posts.body`. The target community is the `social_accounts` row linked via the publication's `social_account_id` if set (rejected with 400 if that account isn't itself a `vk` account, or isn't `active`), else the project's first `active` `vk` account (`ORDER BY created_at ASC`) — same one-active-account-per-project assumption as Telegram. That account's `vk_group_id` (resolved when the community was connected/verified) becomes the VK `owner_id` directly; if it's blank for some reason, the old fallback still runs — `username` (or, if empty, the last path segment of `public_url`) resolved server-side via VK's own `utils.resolveScreenName`, using that same per-account token. A screen name that resolves to `type: 'user'` (a personal profile, not a community) is rejected with 400. `external_url` is built as `https://vk.com/wall<owner_id>_<post_id>` (VK's own canonical permalink format, valid regardless of the community's short name).

No `social_publications` schema change: reuses the same columns as Telegram. On success: `status='published'`, `external_post_id` = VK's `post_id`, `external_url` as above, `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs. On a VK API error (`{"error": {"error_code", "error_msg"}}`), a missing/undecryptable token, or network/resolve failure, the row is set to `status='failed'` with the message in `error`, leaving `external_post_id`/`external_url` untouched — not thrown as an HTTP error, so the route returns 200 with the row and the UI shows it via `publication.error`; calling the endpoint again from `failed` is a normal retry. Calling the endpoint on an already-`published` publication is rejected with 409 before any VK API call (duplicate-send protection); calling it on a non-`vk` publication is rejected with 400. No scheduler or background job — synchronous, on-demand from the button click only. Media/attachments are not supported yet — text-only posts.

Migration: `db/migrations/0021_social_accounts_vk_credentials.sql` (additive: `vk_access_token_encrypted`, `vk_group_id`, `connection_error` on `social_accounts`). Not yet applied to production — must be applied manually (`psql "$DATABASE_URL" -f db/migrations/0021_social_accounts_vk_credentials.sql`), same as every other migration in this repo (the deploy workflow runs no migrations), and the server-only env var `SOCIAL_ACCOUNT_ENCRYPTION_KEY` must be set before any project can connect a VK community (see `.env.example`). Any project previously relying on the old global `VK_ACCESS_TOKEN` must reconnect its VK community through the Accounts UI after this deploys — that credential is no longer read by the publisher.

### Instagram autoposting

MVP automated posting for Instagram only, via the Instagram API with Instagram Login (no linked Facebook Page needed) — same pattern as Telegram/VK autoposting above, but Instagram has no text-only post: every publish needs exactly one image. A mismatch, or a blank `username`, still refuses to publish with a 403.

No migration either time: (1) reads a new env var naming an existing project slug — the same `project_id`/slug mechanism every other project-scoped check in this app already uses, just pinned to a fixed value; (2) still relies entirely on the `username` column that already existed. Known limitations: exactly one project can ever use a platform's global credentials at a time (switching which project owns them is an env var + redeploy, not a UI action); a project whose `social_accounts.username` was never filled in (or filled in with the wrong handle) cannot be auto-posted to Instagram even once it's the named owner — see "Social Accounts" above, where `username` is now load-bearing, not just cosmetic.

Caption is `social_posts.instagram_text` if non-empty, else `social_posts.body` — same fallback pattern as Telegram/VK. The image is `social_posts.instagram_image_url` — populated by the upload control described below, mandatory: publishing is rejected with 400 if it's empty, since Instagram has no text-only post. This is the one schema change autoposting has needed so far (Telegram/VK's own platforms both support text-only posts, so they didn't): `db/migrations/0008_social_posts_instagram_image.sql` added `social_posts.instagram_image_url TEXT NOT NULL DEFAULT ''`.

On success (`media_publish` returned a media id — **the permalink read-back is best-effort and never fatal**, same as Threads already was; see "Reliability fixes (PR-1)" below for why): `status='published'`, `external_post_id` = the published media id, `external_url` = its permalink if the read-back succeeded (empty string otherwise), `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs. On a genuine failure — `media_publish` itself never returned a media id, because of a Meta API error at container creation or publish, the container reporting `status_code=ERROR`/`EXPIRED`, the bounded poll timing out, or a network failure before that point — the row is set to `status='failed'` with the message in `error`, leaving `external_post_id`/`external_url` untouched; not thrown as an HTTP error, so the route returns 200 with the row and the UI shows it via `publication.error`; calling the endpoint again from `failed` is a normal retry. No scheduler or background job — synchronous, on-demand from the button click only. No carousel/Reels/video — single image + caption only.

### Instagram image upload

`social_posts.instagram_image_url` is populated by an upload control in the post edit UI (not manual text entry) — `POST /api/social/upload-instagram-image?project=<slug>` accepts one JPEG (`multipart/form-data`, field `file`), validates it (content-type plus a magic-byte check for the JPEG marker `FF D8 FF`, max 8MB — matching Instagram's own JPEG limit), and rejects anything else with 400. On success the file is written to disk under `<repo>/uploads/instagram/<project-slug>/<crypto.randomUUID()>.jpg` (original filename is never used, so there's no user-controlled path segment) and the route returns the absolute URL `GET /api/social/instagram-image/<project>/<filename>` serves it from — the client immediately PATCHes that URL into `instagram_image_url` (`components/sections/social-view.tsx`'s `handleImageUpload`), the same way the Publish buttons auto-save their own result, rather than waiting for the post's general Save button.

No S3/R2/new storage service, no Nginx/systemd change, no base64 in Postgres, no heavy media in Git (`uploads/` is gitignored). The uploaded file is **not** served through Next's `public/` folder convention — a root-level static request in this Next.js version collides with the `app/[locale]` dynamic segment and 404s before the file is ever checked (confirmed by direct testing: even a file present at build time under `public/` returned 404 the same way an unmatched locale does). So it's served instead by an explicit route handler, `GET /api/social/instagram-image/[project]/[filename]` (`lib/social-instagram-uploads.ts` holds the shared storage-path constant and the strict allow-list regexes both routes validate against — a numeric-UUID-shaped filename and a lowercase-alphanumeric-hyphen project slug — so a path-traversal attempt can never reach the filesystem call), which reads the file itself and returns it with `Content-Type: image/jpeg` and a long immutable `Cache-Control` (safe since filenames are fresh, never-reused UUIDs). `PUBLIC_SITE_URL` (non-secret env var, default `https://admin.olnoo.com`) turns the saved file into the absolute HTTPS URL Instagram's API needs to fetch it from — same non-secret-override role as `TELEGRAM_API_BASE_URL`/`VK_API_BASE_URL`.

This relies on OLNOO Admin running as a single server process with a persistent filesystem (confirmed: one systemd service, one port, no load balancer) — uploaded files live on that one server's disk. `git reset --hard origin/main` in the deploy workflow does not touch untracked files, so uploads survive a deploy. If the app is ever horizontally scaled, this would need real object storage instead. No cleanup job for orphaned files (e.g. after replacing an image or deleting a post) — out of scope for this MVP.

Before the file is written to disk, it's passed through `lib/social-instagram-image-normalize.ts` (`normalizeInstagramImageBuffer`) to guarantee an Instagram Feed-valid aspect ratio and max width — see "Instagram image aspect ratio normalization" below. That step doesn't add a new dependency on storage or a media service; it's a synchronous in-process transform using `jimp` (a pure-JS image library — no native binary, so nothing new for the KZ deploy's `npm ci` to compile), same request, same route, same disk.

### Instagram image aspect ratio normalization

Root cause this fixes: `lib/social-instagram.ts`'s `publishSocialPublicationToInstagram` (untouched by this) was rejecting real posts with Instagram's own `"The aspect ratio is not supported."` error, and separately, large images (e.g. 4000-6000px wide) with an already-valid ratio were failing to publish at all — the upload step accepted any JPEG shape/size. Instagram's Content Publishing API for Feed images only accepts an aspect ratio between **4:5 (portrait) and 1.91:1 (landscape) inclusive**, and a width of at most **1440px** (confirmed against Meta's current `developers.facebook.com/docs/instagram-platform/content-publishing/` docs; a too-small width is auto-scaled up by Instagram's own servers, but a too-large one was observed in production to fail rather than being scaled down server-side, so this handles the max-width side itself).

Fixed entirely at upload time, in `POST /api/social/upload-instagram-image` (the only place a file becomes `instagram_image_url`), not in the publish flow: after the existing magic-byte/size checks, the buffer goes through `normalizeInstagramImageBuffer` (`lib/social-instagram-image-normalize.ts`) before ever being written to disk. The user's own frame is **never cropped** — an earlier version of this normalizer cropped out-of-range images to fit, which silently discarded part of the photo (wrong UX, reported and replaced). A later version fixed that by letterboxing on flat white, which was itself reported as looking bad (large dead white/black bars) and replaced with a blurred-background version. The current algorithm always keeps the entire original frame and never shows a flat empty bar:
1. **Ratio already valid (4:5–1.91:1)** — the whole frame is kept as-is; only **width** is handled: if it still exceeds **1440px**, the image is proportionally resized down to width 1440 (height scaled by the same factor — never distorted, never cropped). Computed by the pure, unit-tested `computeInstagramFeedResize(width, height)`.
2. **Ratio out of range** — a canvas is sized at the *nearer* valid ratio edge (a too-wide landscape, ratio > 1.91:1, targets **1.91:1**; a too-tall portrait, ratio < 4:5, targets **4:5** — the nearer edge rather than always 4:5 keeps the foreground as large as possible), capped at **1440px** wide. Geometry computed by the pure, unit-tested `computeInstagramFeedContain(width, height)` (`isInstagramFeedRatioAllowed` decides which of the two cases applies; `computeInstagramFeedContain` returns `null` when the ratio is already valid, in which case only step 1 applies). Two independent renders of the *same* source image fill that canvas:
   - **Background** — a clone of the source is scaled+cropped to exactly *cover* the full canvas (`jimp`'s `cover({w,h})`; cropping here is fine, it's decorative, never the frame the viewer is meant to read) then run through a strong box blur (`jimp`'s `blur(r)`, radius ~8% of the canvas's shorter side, capped at 100px) so it reads as an abstract color wash, not a legible duplicate.
   - **Foreground** — the source, proportionally scaled down to fit entirely inside the canvas without cropping or distortion (never upscaled), composited centered on top of the blurred background via `blit({src,x,y})`.

An image that needs neither step (already-valid ratio, width ≤ 1440) has its bytes returned completely unchanged — no re-encode, no quality loss, no behavior change for the common case. Otherwise the result is re-encoded via `jimp`'s JPEG encoder (`quality: 92`) and re-checked against the same 8MB cap the original upload already enforced. Because normalization happens before the file is saved, the same served URL (`GET /api/social/instagram-image/[project]/[filename]`) the post's preview `<img>` and the publish flow both use is always the final, already-normalized file — nothing downstream (preview, `social_posts.instagram_image_url`, `lib/social-instagram.ts`, `social_publications`) needed to change.

`jimp` (pure JS, no native/binary dependency — confirmed via its own `package.json`, unlike e.g. `sharp`) is used only for this: decode buffer → read `width`/`height` → `clone()` → `cover({w,h})` + `blur(r)` for the background → optionally `resize({w,h})` the foreground copy → `blit({src,x,y})` to composite → `getBuffer('image/jpeg')`. `cover()`'s own crop is only ever applied to the decorative background clone, never to the foreground/primary frame. Deliberately not `sharp` or another native-binding library, to avoid adding a platform-specific compiled dependency to the KZ deploy's plain `npm ci && npm run build`.

### Threads autoposting

### Publish selected channels (fan-out)

A single "Publish selected channels" button in the post's Publications block that replaces having to click Telegram/VK/Instagram/Threads's four individual "Publish to X" buttons one at a time — pure orchestration, no new publish logic: it calls the same four publisher functions above, once each, and reuses their existing per-platform behavior (including each one's own 409 duplicate guard) unchanged.

`POST /api/social-publications/publish-selected?project=<slug>` (body `{ postId }`; `lib/social-publish-selected.ts`, project-scoped through `resolveProjectId`) reads the post's currently-selected `channels` and its `social_publications` rows, then for every selected channel whose row isn't already `published`, calls that platform's existing publisher (`publishSocialPublicationTo{Telegram,Vk,Instagram,Threads}`) — channels already `published` are skipped without any API call. `publishSelectedChannels(pool, postId, projectSlug, { retryFailed? })` takes an optional `retryFailed` (default `true`, filtered through the pure `shouldAttemptPublicationTarget` in `lib/social-publish-selected-targets.ts`): this manual route keeps the default, so a channel already `status='failed'` is retried like any other — only the scheduler (below) passes `retryFailed: false`. Every call runs independently (`Promise.all` over per-channel calls that each catch their own exceptions) — one channel's platform error, or even a thrown exception, never stops or is reported against another. Instagram's existing "no `instagram_image_url`" pre-flight rejection is not special-cased here; it's the same `{error, status:400}` any other pre-flight failure returns, surfaced as that channel's own failure while the rest of the run continues. The pure result-shaping (mapping a publisher's `{error,status}`/`{row}` result to `published`/`failed`/`already_published`, including treating a 409 hit mid-run — e.g. a concurrent publish between this endpoint's own read and its call — as `already_published` rather than `failed`) lives in `lib/social-publish-selected-outcome.ts`, kept dependency-free so it's unit-tested directly (`lib/social-publish-selected-outcome.test.ts`) the same way `lib/social-threads-text.ts` is.

Response: `{ results: [{ id, platform, outcome: 'published'|'failed'|'already_published', externalUrl, error }, …] }` — one entry per currently-selected channel, in the same shape the UI renders as its "Last run" panel (`components/sections/social-publications.tsx`). The button itself (`shouldShowPublishSelectedButton` in `lib/social-publications-ui.ts`) only shows while the post isn't yet fully published; after a run it refetches `social_publications`/`social_accounts` so every individual channel row (status pill, external URL, retry button) reflects the outcome immediately, same as clicking that channel's own button would. A channel that failed keeps its individual "Publish to X" button for a normal retry — this feature adds no new retry mechanism of its own. No schema change (reuses `social_publications`/`social_posts` as they already are), no queue, no cron, no separate service.

### Social scheduler (auto-publish by publish_date)

Ready posts publish themselves once their `publish_date` arrives, with no one having to open Admin — pure scheduling on top of the fan-out above, not new publish logic: each due post is handed to the exact same `publishSelectedChannels` the "Publish selected channels" button calls.

`publish_date` stayed a plain `TEXT` column — no migration. It always was free-form text (previously written by an `<input type="date">`, `"YYYY-MM-DD"`); the post edit UI now uses `<input type="datetime-local">`, writing `"YYYY-MM-DDTHH:mm"` (no timezone offset) into the same column. Both shapes parse with the native `Date` constructor, though per the ECMA-262 Date Time String Format they're interpreted differently — a date-only string as UTC midnight, a date-time string with no offset as local time in whatever timezone the Node process runs (KZ production's timezone) — an intentional, documented simplification for a single-server MVP rather than pulling in a timezone library. `lib/social-scheduler-due.ts` (`parsePublishDate`, `isPublishDue`) is the one place that logic lives, dependency-free and unit-tested (`lib/social-scheduler-due.test.ts`). The input's display/edit value and the Posts list column both go through `lib/social-publish-date-format.ts` (`toDatetimeLocalInputValue` upgrades a legacy date-only value to midnight so it's still editable in the new control; `formatPublishDate` shows date+time when the stored value carries a time, date-only otherwise), also dependency-free and unit-tested.

`lib/social-scheduler.ts`'s `runSocialScheduler(pool, now?)` is the sweep: finds every `social_posts` row where `status='ready'`, `channels <> ''`, `publish_date <> ''` and `isPublishDue(publish_date)`, and at least one of its `social_publications` rows isn't `'published'` yet (a plain SQL query joined to `projects` for the slug `publishSelectedChannels` needs, then filtered by `isPublishDue` in application code, not SQL, since `publish_date` is text) — then calls `publishSelectedChannels(pool, post.id, post.slug, { retryFailed: false })` on each, one at a time (sequential, not parallel, to keep load on the one production server and its DB pool predictable during a catch-up sweep after any downtime). `retryFailed: false` is what makes a sweep different from a human clicking "Publish selected channels": a channel already `status='failed'` is never automatically retried by the scheduler (see "Reliability fixes (PR-1)" below) — it still shows up in the scheduler's candidate query (a post with one `failed` and one never-tried channel is still "due"), but that one channel is simply skipped by this call, at no API-call cost. A post with no `publish_date` set at all is never picked up — unchanged, intentional manual-publish behavior for posts that were never given a schedule. One post's unexpected exception (distinct from a single failed channel, which `publishSelectedChannels` already isolates) is caught per-post so it can't stop the sweep over the remaining due posts. Because `publishSelectedChannels` already skips channels that are `published` and defers to each publisher's own 409 guard, and because `syncPostStatusFromPublications` already runs after every publication write, a fully-succeeded sweep leaves the post `status='published'` and a partially-failed one leaves it `'ready'` (not fully published), with `failed` channels now needing a human's manual retry rather than being retried automatically — both entirely via existing mechanisms, nothing scheduler-specific.

Overlap protection for "two scheduler runs at once" (the one new concern this feature adds — per-channel duplicate protection already existed) is a single Postgres session-level advisory lock (`pg_try_advisory_lock`/`pg_advisory_unlock`, fixed key `727142001`) held for the whole sweep, not per-post or per-project — the simplest mechanism the current Postgres already offers, no new table, no queue, and nothing to clean up if the process dies (the lock releases itself with the DB session). A run that finds the lock already held returns `{skipped: true}` immediately rather than waiting or queuing. **Acquired, held, and released through one dedicated connection** (`lib/social-scheduler-lock.ts`'s `withSchedulerLock`, via `pool.connect()`) — not through `pool.query()` for each of the two calls independently, which could silently run the acquire and release on two different pooled connections (an advisory lock is tied to the specific Postgres backend/session that took it, not to the pool as a whole); see "Reliability fixes (PR-1)" below.

Trigger, chosen over the alternative of a public/authenticated client-facing endpoint or a standalone script: `POST /api/social-scheduler/run` (`app/api/social-scheduler/run/route.ts`) — an ordinary Next.js route (so it can reuse `@/lib/*` the same as every other Social route, unlike a standalone script run via plain `node`, which can't resolve that path alias outside the Next build) called once a minute by a **systemd timer** on the same KZ server via `curl` against `127.0.0.1:3140` — never through nginx or the public domain, so no nginx change was needed. Protected by a shared-secret header (`X-Scheduler-Token`, checked against the server-only env var `SOCIAL_SCHEDULER_TOKEN`) rather than an IP/localhost check, since this app has no trusted-proxy header handling to lean on and nginx wasn't touched to add any — the same shared-secret-header idiom `OLNOO_CRM_API_KEY`/`/api/leads/inbound` already uses. Unset `SOCIAL_SCHEDULER_TOKEN` is a hard 500 refusal, never an open door. Reference unit files and the exact one-time KZ install steps live in `deploy/social-scheduler/` (not wired into `.github/workflows/deploy.yml` — installed once by hand, per that folder's `README.md`); a cron entry would work equally well but wasn't added alongside the timer, to avoid two competing triggers.

### Automatic Instagram/Threads token refresh (daily sweep)

Keeps the per-account Instagram/Threads credentials from "Instagram/Threads account connection — Social Connect MVP" above refreshed BEFORE they expire, without a human having to open the account and click "Recheck connection" on a schedule. Built as its own independent sweep, reusing the exact trigger pattern the Social scheduler above already established (systemd timer → authenticated internal route) — **not** a new service, queue, or Redis, and **not** folded into `lib/social-scheduler.ts`'s own once-a-minute publish sweep: that function's atomic-claim/advisory-lock invariants were specifically hardened by "Reliability fixes (PR-1/PR-2)" below to stay narrow, and a ~60-day token window has no need for minute-level polling — widening that sweep's scope and lock-hold time for this was evaluated and rejected when Social Connect MVP shipped (see the note above).

- **Core sweep:** `lib/social-meta-token-refresh-sweep.ts`'s `refreshExpiringMetaTokens(pool, windowDays = REFRESH_WINDOW_DAYS)`. Selects every `social_accounts` row, any project, whose `instagram_token_expires_at`/`threads_token_expires_at` is set, **not yet expired**, and within `windowDays` of expiring; refreshes each independently via the existing `refreshInstagramLongLivedToken`/`refreshThreadsLongLivedToken` (`lib/social-meta-token-refresh.ts`, reused as-is, not rewritten), sequentially (same "keep load predictable" reasoning as the publish sweep above). Never tracks a separate "token issued at" timestamp to check Meta's 24h-minimum-refresh-age rule directly — by construction, a token only enters the selection window after living for roughly 53+ days of its ~60-day life, so the 24h minimum is always already satisfied. An already-EXPIRED token is explicitly excluded (Meta's refresh endpoint cannot revive one anyway) — it keeps failing closed at publish time with the existing clear "reconnect" error (see "Credential resolution order" above), unchanged.
- **`REFRESH_WINDOW_DAYS = 7` lives in its own zero-dependency module, `lib/social-meta-token-refresh-window.ts`** (review fix) — not in the sweep module itself. The sweep (`lib/social-meta-token-refresh-sweep.ts`) and the Accounts UI (`components/sections/social-accounts-view.tsx`, a `'use client'` component) both need this one number; having the UI import it straight out of the sweep module would drag the whole server-only module — the `pg` client, the decrypt/refresh network calls — into the client bundle just to read a constant. The tiny shared module has nothing else in it, so the client bundle only ever sees that one export; the sweep module no longer defines or re-exports the constant itself, keeping one source of truth.
- **A failed refresh never disables a still-working connection.** Whether Meta rejects the refresh call or the stored ciphertext fails to decrypt, only `connection_error` is updated (for visibility) — `status` and the existing token/expiry are left exactly as they were. One account's failure never affects any other account's attempt (same per-item isolation as `lib/social-publish-selected.ts`'s own per-channel independence).
- **Atomic, non-clobbering update — both on success AND on a failure.** The success-path `UPDATE` is conditioned on the EXACT ciphertext this sweep read moments earlier (`WHERE id = $id AND project_id = $projectId AND <token_column> = $theSnapshotJustRead`), not a blind overwrite. If a concurrent manual "Recheck connection" (or an overlapping sweep run) already wrote a different token for that account in between, this `UPDATE` matches zero rows and the sweep's own, now-stale, result is discarded rather than clobbering the newer one. **The `connection_error` write on a failed refresh is guarded by the exact same pin** (review fix) — without it, a stale "refresh failed" error could land on an account a concurrent reconnect had *already fixed* in the meantime, showing a false error next to a connection that is actually fine; the guard means that write, too, is silently discarded when the token has moved on. Both paths proven with a real concurrent write racing the sweep in `lib/social-meta-token-refresh-sweep.test.ts`. AES-256-GCM's random IV per encryption means this equality check can only ever match the literal snapshot read, never a different real update that happens to decrypt to the same plaintext.
- **Project isolation:** every query is scoped by `id AND project_id` together; the sweep scans accounts across all projects but each row's own update can only ever affect that row's own project — verified directly with two different projects' expiring tokens refreshed in the same sweep run, neither touching the other.
- **Trigger:** `POST /api/social-token-refresh/run` (`app/api/social-token-refresh/run/route.ts`), called once a day by its own systemd timer (`deploy/social-token-refresh/`, `OnCalendar=*-*-* 03:17:00`) via `curl` against `127.0.0.1:3140` — same never-through-nginx pattern as the publish scheduler. **Reuses the same `SOCIAL_SCHEDULER_TOKEN` env var and `X-Scheduler-Token` header** as `/api/social-scheduler/run` — a second, independent trigger, not a second secret to provision, since the trust boundary (this same server, localhost-only) is identical; the two sweeps touch disjoint tables (`social_accounts` here, `social_publications` there) with no shared lock, so they can run concurrently without interfering. Not wired into `.github/workflows/deploy.yml` — installed once by hand, per `deploy/social-token-refresh/README.md`.
- **UI:** the Accounts detail drawer (`components/sections/social-accounts-view.tsx`) shows a derived (not persisted — no new `social_accounts.status` value, no migration) "expires in N day(s)" / "expired" line next to a connected Instagram/Threads account's status, warning-styled once within the same `REFRESH_WINDOW_DAYS` the sweep itself uses (imported from `lib/social-meta-token-refresh-window.ts`, never from the sweep module, so the two can never drift apart and the client bundle never pulls in server-only code).
- **No change** to `lib/social-scheduler.ts`, the Social Publisher send logic, VK/Telegram, or the global `OWNER_PROJECT`-gated env fallback.

### OLNOO Social AI Agent MVP

Turns one free-text task written by a project's own admin (e.g. "Prepare three posts for the week about car polishing for DriveSet") into several REAL draft rows in Social Posts, tied to that project — a compact "AI Agent" block inside the existing Social screen, not a new app/page. No automatic sending or scheduling of any kind: every created post is `status='draft'`, `publish_date=''`, exactly like a post an admin created by hand through "+ Add post" and hasn't touched yet — it only ever becomes `ready`/scheduled/published through the existing Social Posts UI and scheduler above, unchanged.

- **Reuses, does not duplicate:** the existing AI Router (`lib/ai-router.ts`'s `callAiRouter`, the same client `lib/social-ai.ts` and the SEO modules already use — no new provider), the existing per-channel adaptation (`generateChannelVariants`, `lib/social-ai.ts`), and the existing post CRUD (`createSocialPost`/`deleteSocialPost`, `lib/social.ts`). No new AI Router, agent service, queue, Redis, separate DB, or timer.
- **`lib/social-agent-plan.ts`** — pure, dependency-free module (no `@/` imports, directly testable under this project's plain `node --test` the same way `lib/social-scheduler-due.ts` is): `buildSocialAgentPlanPrompt`/`SOCIAL_AGENT_PLAN_SYSTEM_PROMPT` build the one prompt sent to the AI Router (post count inferred from the task's own wording, default 3; topic/body written in the task's own language, never translated); `parseSocialAgentPlan(raw, availableChannels)` validates the model's JSON response — a channel outside the project's own connected channels is dropped from a post rather than invented, a post left with zero usable channels or a missing topic/body is dropped entirely, the result capped at 10 items, and a `SocialAgentPlanError` is thrown (never a raw parse exception) if nothing usable survives.
- **`lib/social-agent.ts`'s `runSocialAgentTask(pool, projectId, runId, task, deps)`** is the orchestrator: resolves the project's connected channels (`social_accounts` with `active=true`, same convention Telegram/VK/Instagram/Threads autoposting already assume) → fails closed (400) if none are connected → claims the run (idempotency, see below) → calls the AI Router to plan → per planned item, adapts + creates one real draft via the injected `deps.createAdaptedDraftPost` → on full success, marks the run `completed` and returns the created posts.
  - **Dependency injection (`SocialAgentDeps`), not a direct import — and why:** `lib/social.ts`/`lib/social-ai.ts` both import `@/lib/db`/`@/lib/crm`, which this project's plain `node --test` runner cannot resolve (no path-alias loader configured; this is a pre-existing gap — neither file has ever had a test file of its own, confirmed before writing any of this feature's code, not introduced by it). So `lib/social-agent.ts` takes the "adapt + create" and "delete" steps as an injected `SocialAgentDeps` — same shape and same reasoning as `lib/telegram-comments-handler.ts`'s existing `TelegramCommentsDeps` — keeping the orchestration/idempotency logic (the actually-new part) fully unit-testable under `node --test`, while `app/api/social/agent-task/route.ts` is the one place that wires the injected functions to the real `createSocialPost`/`generateChannelVariants`/`deleteSocialPost`.
  - **No partial set on failure (requirement):** every AI Router call happens entirely before any `social_posts` row is written — a planning failure (AI Router error, or an unparseable/empty response) creates zero posts. If the per-item create loop itself fails partway (an AI Router error during per-channel adaptation, or a post-creation error), every post this run already created is rolled back via `deps.deletePost` before the run is marked `failed` — the end state is always "zero drafts from this run", never a partial batch.
  - **Idempotency (requirement: repeating the confirmation never creates duplicates):** `db/migrations/0027_social_agent_runs.sql` adds `social_agent_runs` — the one new table this feature needs, since nothing existing can durably record "this specific free-text run was already processed" without overloading another column's own meaning (e.g. the legacy `social_posts.category` column is documented elsewhere as no longer written to). The client mints one `runId` (`crypto.randomUUID()`) per logical "run" and resends the SAME value when retrying the SAME attempt (a double click, a network retry) — a genuinely new task gets a fresh id. The claim is the same atomic shape `db/migrations/0026_social_comment_replies.sql` introduced for Telegram reply retries: `INSERT … ON CONFLICT (id, project_id) DO UPDATE … WHERE status = 'failed' RETURNING id`. A fresh (id, project) pair is claimed by the INSERT itself; a pair already `completed` is never reclaimed — the caller instead replays the SAME `post_ids` (so repeating a confirmation is a no-op, never a second batch); a pair still `running` is refused with 409 (a genuinely concurrent duplicate); only a CONFIRMED `failed` run can be retried with the same id. The primary key is the composite `(id, project_id)`, not `id` alone — `runId` is an idempotency key scoped to one project, so a plain `id PRIMARY KEY` would let the SAME id collide across two different projects at the `ON CONFLICT` level before any project check runs; every read is additionally scoped by `WHERE project_id = …` as defense in depth.
- **`POST /api/social/agent-task`** (body `{ project, task, runId? }`) — the only place the real `createSocialPost`/`generateChannelVariants`/`deleteSocialPost` are wired to the agent; `runId` defaults to a fresh server-generated one if the client omits it, but the client is expected to mint and reuse its own for retry-safety. Returns `{ runId, replayed: false, posts: [{id, topic, channels}] }` on a fresh run, `{ runId, replayed: true, postIds }` on a replayed confirmation, or `{ error, status }` (400 bad input/no connected channel, 409 already running, 422 AI Router/plan failure).
- **UI:** a compact "AI Agent" block inside the existing Social screen (`components/sections/social-view.tsx`'s `SocialAgentBlock`, rendered only for a specific project — never for "All projects", same as the existing "+ Add post" form's own project requirement), between the status metrics and the search/filter row. A free-text task textarea, a Run button, and a result/error line — no separate page, no redesign of the existing Posts table/`PostDetail` editor. The client mints its own `runId` once per task and reuses it across retries of that same attempt (cleared only when the task text itself is edited), mirroring the idempotency contract above. On success, the block asks `SocialView` to reload the project's posts list (`GET /api/social?project=…`, since the agent's own response only carries `{id, topic, channels}`, not every field `PostDetail` needs) — the new drafts then appear in the existing table and open in the existing `PostDetail` editor exactly like any other post, satisfying "drafts open in the existing Social interface" without any agent-specific viewer.
- **Tests:** `lib/social-agent-plan.test.ts` (pure, 12 cases — prompt construction, channel filtering, missing-field/empty-channel drops, the 10-item cap, invalid/non-array JSON). `lib/social-agent.test.ts` is a real-Postgres integration suite (skipped if unreachable, same convention as `lib/social-comment-reply.test.ts`) with a FAKE `SocialAgentDeps` standing in for the reused `createSocialPost`/`generateChannelVariants` (which cannot themselves be loaded under `node --test`, see above): multi-post creation, project isolation with a shared `runId` reused across two different projects, no-connected-channel refusal, dedup replay, a concurrent-race test (two simultaneous calls with the same `runId` — exactly one ever actually runs the agent; the other is refused with 409 or, if it only reaches the claim after the winner has already fully committed, correctly sees a replay of the same result instead — both are valid outcomes of the same idempotency guarantee, so the test accepts either), AI Router HTTP-error and unparseable-JSON failures (both zero posts), a partial-creation-failure rollback, and a failed-run retry with the same `runId`. **Not verified by this file's own `node --test` run:** the real `createSocialPost`/`generateChannelVariants`/`deleteSocialPost` wiring in `app/api/social/agent-task/route.ts` itself (same `@/`-import limitation as above) — confirmed instead via `npx tsc --noEmit` and `npx next build` (the route appears in the build's route list) plus manual review, not an end-to-end run against a live deploy.
- **Does not touch:** SEO, CRM, Ads, Nginx, systemd, GitHub Actions, `lib/social-scheduler.ts`, the Social Publisher send logic, or any existing Social Posts/AI function's own implementation.

### Reliability fixes (PR-1): infinite automatic retries and confirmed duplication paths

Five fixes to the scheduler/publisher fan-out above, from a risk analysis of the Social Publisher, none involving a schema change, a new table, a queue, a heartbeat, or an automatic-retry system — each reuses or minimally extends what already existed:

1. **The scheduler never automatically retries a `failed` publication.** `publishSelectedChannels` (`lib/social-publish-selected.ts`) takes an optional `retryFailed` (default `true`), filtered through the pure `shouldAttemptPublicationTarget` (`lib/social-publish-selected-targets.ts`); `runSocialScheduler` passes `retryFailed: false`, the manual "Publish selected channels" route/button and the individual "Publish to X" buttons keep the default. Before this, a durable, known failure (bad credentials, missing content, a platform rejecting the content outright) was retried automatically by the scheduler every sweep — once a minute, forever — with no way to stop short of a human intervening. A human can still deliberately retry a `failed` channel at any time; only the *automatic* retry is gone.

2. **A pre-flight problem (before any platform API call) is now persisted onto the row as `status='failed'`, same as a platform API failure already was.** `lib/social-publication-preflight-failure.ts`'s `recordPublicationPreflightFailure(pool, id, projectId, message)` is called from every pre-flight `{error, status}` branch in `lib/social-telegram.ts`/`lib/social-vk.ts`/`lib/social-instagram.ts`/`lib/social-threads.ts` (no account configured, no content, no token, an undecryptable credential, the project-ownership gate, …) before returning — each call site's own `{error, status}` response to the caller is unchanged. Before this fix, a pre-flight problem left the row in whatever non-terminal status it already had (`draft`/`ready`), so the scheduler's own `WHERE pub.status <> 'published'` candidate query kept matching it and re-attempting the exact same doomed-to-fail call forever — fix 1 alone wouldn't have helped, since the row was never actually `failed` to begin with.

3. **Instagram: a successful `media_publish` is reported as `published` even if the trailing permalink lookup fails.** `lib/social-instagram-publish-outcome.ts`'s pure `resolveInstagramPublishOutcome(mediaId, permalink, igError)` decides this — `mediaId` (set only once `media_publish` itself succeeded) alone determines success; a permalink-lookup failure only ever leaves `external_url` blank. Threads' own publisher (`lib/social-threads.ts`) already got this right; Instagram's now matches it. This was a genuine duplication risk, not just a cosmetic one: a `failed` row doesn't trip the "already published" 409 guard every publisher has, so a retry (manual, or — before fix 1 — an automatic scheduler retry) of a publication that was actually already live on Instagram would call `media_publish` a second time and post the same content twice.

4. **A `published` publication can never be moved back to `'ready'`, in either the UI or the API.** `lib/social-publication-status-transition.ts`'s pure `isForbiddenPublicationStatusTransition(currentStatus, nextStatus)` (true only for `published → ready`) is checked in `updateSocialPublication` (`lib/social-publications.ts`, backing `PATCH /api/social-publications/[id]`) before applying any status change; a forbidden transition is refused with 400. The UI's own "Back to ready" button (`components/sections/social-publications.tsx`) — the only reachable path to this transition — is removed outright rather than merely guarded, since there's no legitimate reason to show a control the API will always refuse. This was the other confirmed duplication path: `status='published'` is the one thing every publisher's own 409 guard checks, so erasing it (to `'ready'`, specifically — every other transition is still allowed) silently re-enabled a next publish attempt to recreate the same post on the real platform, even though nothing had actually changed there.

5. **The scheduler's Postgres advisory lock is acquired, held, and released through one dedicated connection.** `lib/social-scheduler-lock.ts`'s `withSchedulerLock(pool, fn)` uses `pool.connect()` to check out a single physical connection for the whole lock lifecycle, replacing two independent `pool.query()` calls (one for `pg_try_advisory_lock`, one for `pg_advisory_unlock`) that could each land on a *different* pooled connection — since an advisory lock is tied to the specific Postgres backend/session that took it, not to the pool as a whole, a mismatched acquire/release could make the unlock a silent no-op while the lock stayed held on some other, now-idle connection, defeating the one-sweep-at-a-time guarantee the lock exists for. `runSocialScheduler` is otherwise unchanged — the candidate query and the per-post `publishSelectedChannels` calls still run through the ordinary `pool`.

Regression tests: `lib/social-publish-selected-targets.test.ts`, `lib/social-instagram-publish-outcome.test.ts`, and `lib/social-publication-status-transition.test.ts` are pure, dependency-free unit tests; `lib/social-scheduler-lock.test.ts` and `lib/social-publication-preflight-failure.test.ts` are DB-integration tests (same gracefully-skipped-without-Postgres convention as `lib/crm-observer.test.ts`) that exercise the real `pg_try_advisory_lock`/`UPDATE` calls; `lib/social-publisher-reliability-wiring.test.ts` is a static source-text guard confirming each `@/`-aliased file actually calls the above. The full flow (scheduler sweep → preflight persistence → Instagram permalink failure → published→ready refusal → manual-vs-automatic retry) was also verified manually against a real local Postgres with the four platform API base URLs pointed at a local mock HTTP server (`TELEGRAM_API_BASE_URL`/`INSTAGRAM_API_BASE_URL`/etc.) — no real Telegram/VK/Instagram/Threads call was made and no real post was published.

### Reliability fixes (PR-2): atomic capture, a new `publishing` status, and unconfirmed-outcome handling

PR-1 (above) stopped the scheduler from automatically retrying a *known* failure. PR-2 closes the two risks that remained: two processes (typically the "Publish selected channels" button and the scheduler, firing within the same minute) racing to publish the same row, and a send whose real-world outcome is never actually confirmed (a timeout or a dropped connection, not a response from the platform saying "yes" or "no"). Still no schema change, new table, queue, service, or automatic-retry mechanism — `social_publications.status` is a plain `TEXT` column with no `CHECK` constraint (confirmed against `db/migrations/0007_social_accounts_publications.sql`), so adding `'publishing'` as a new value needed no migration at all.

1. **Atomic capture, via Postgres, right before the one irreversible call to the platform.** `lib/social-publication-claim.ts`'s `claimPublicationForSending(pool, id, projectId)` runs a single `UPDATE social_publications SET status = 'publishing', updated_at = now() WHERE id = $1 AND project_id = $2 AND status NOT IN ('publishing', 'published') RETURNING *`. Postgres's own row-level locking makes this atomic: under two concurrent calls for the same row, the second blocks on the first's lock, then re-evaluates its `WHERE` against the first's already-committed write, so it affects zero rows. At most one caller's claim ever returns `claimed: true`; the loser gets `claimed: false` (`publicationClaimConflictResult` maps this to a 409, reusing the same status the pre-existing "already published" guard already used) and never calls the platform. Verified under real concurrency, not just in theory: `lib/social-publication-claim.test.ts` fires 2 and then 10 simultaneous claims at the same row against a real Postgres and asserts exactly one ever wins.

2. **`'publishing'` is the status for a publish attempt currently in flight.** Each publisher calls the claim at one precise point — right before its platform's one actual "post it" call (Telegram's `sendMessage`, VK's `wall.post`, Instagram's `media_publish`, Threads' `threads_publish`) — never earlier: every pre-flight check (content, account, token, the project-ownership gate, VK's `resolveOwnerId`, Instagram/Threads' container creation and processing poll) is a safe-to-repeat local read or a call that doesn't itself post anything, so a failure there is still a normal, immediately-persisted `'failed'` (PR-1's `recordPublicationPreflightFailure`), not `'publishing'`.

3. **A definitive platform rejection is still `'failed'`, unchanged from PR-1/the original implementation.** If the send call gets ANY response from the platform — success or a rejection — that's a confirmed outcome either way, written to the row exactly as before.

4. **An unconfirmable outcome (timeout, dropped connection, the process dying mid-request) is never written as `'failed'` and never auto-retried.** Each publisher wraps only its own send call with `signal: AbortSignal.timeout(20_000)` and a dedicated `sendOutcomeUnknown` flag, set ONLY in that call's own `catch` (a thrown `fetch()` — it never got a response at all, confirmed vs. unconfirmed is a property of *that one call*, not of the whole function). When set, the publisher does NOT write anything further — the row is deliberately left at `'publishing'` from the claim — and returns `{error, status: 503}` instead, surfaced by `outcomeFromPublisherResult` (`lib/social-publish-selected-outcome.ts`) as a new `'unknown'` fan-out outcome, distinct from `'failed'`, so the UI never implies "safe to retry" for something that might already be live. A process crash between the claim and the final write produces the identical end state (`'publishing'`, nothing further written) with no code needed for it at all — there's simply nothing left to run.

5. **A confirmed success is still saved exactly once.** Unchanged from before PR-2: the final `UPDATE ... SET status = 'published', ...` write.

6. **No automatic re-capture of a stuck `'publishing'` row, ever.** Multiple independent layers, deliberately redundant: (a) the claim's own `WHERE status NOT IN ('publishing', 'published')` refuses it forever, for every caller, automatic or manual; (b) `shouldAttemptPublicationTarget` (`lib/social-publish-selected-targets.ts`) now also excludes `'publishing'` from the fan-out's own target list, regardless of `retryFailed`, so neither the scheduler nor the manual bulk-publish button even attempts the claim; (c) `isForbiddenPublicationStatusTransition` (`lib/social-publication-status-transition.ts`) refuses to let `PATCH /api/social-publications/[id]` move a `'publishing'` row to ANY other status at all (tightened by the review follow-up below — see why `→ failed`/`→ published` aren't safe either). The Publications UI (`components/sections/social-publications.tsx`) also stops offering any "Publish to X"/"Mark as published" button for a `'publishing'` row (`shouldShowPublishButton` in `lib/social-publications-ui.ts`), showing a plain "Publishing…" label instead, so there's no click that would just bounce off the claim with a confusing 409.

7. **Project isolation and all four platforms are unaffected.** The claim itself takes `projectId` and is scoped by it exactly like every other query in these files; no new cross-project read or write path exists. Verified manually (below) for Telegram and Instagram; VK and Threads got the identical restructuring (claim before the send call, the send call's own `catch` wrapped as `sendOutcomeUnknown`) and are covered by the same wiring tests.

Regression tests: `lib/social-publication-claim.test.ts` (DB-integration, the concurrency proof above); `lib/social-publish-selected-targets.test.ts`, `lib/social-publish-selected-outcome.test.ts`, `lib/social-instagram-publish-outcome.test.ts`, `lib/social-publication-status-transition.test.ts`, `lib/social-publications-ui.test.ts` (all extended with PR-2 cases, pure unit tests); `lib/social-publisher-reliability-pr2-wiring.test.ts` (static source-text guard confirming all four publishers actually call the claim at the right point, bound their send call with the timeout, and only set `sendOutcomeUnknown` from that one call's own `catch`). Manually verified end-to-end against a real local Postgres with `TELEGRAM_API_BASE_URL`/`INSTAGRAM_API_BASE_URL` pointed at a local mock HTTP server (one of them configurable per-request to simulate a dropped connection via a destroyed socket, never a real timeout wait): two genuinely concurrent `POST .../publish-telegram` calls on the same draft publication — one returned `200` (published), the other `409`; a dropped-connection send returned `503` and left the row at `'publishing'`, `error` untouched; a scheduler run right after that left the stuck row completely alone (`outcomes: []` for that channel, `updated_at` unchanged); a definitive rejection (`mode=error` on the mock) wrote `'failed'` with the platform's message; project isolation held (`project=driveset` against an `olnoo` publication id → `404`); Instagram's claim-gated flow published successfully end-to-end through the same mock setup PR-1 used. No real Telegram/VK/Instagram/Threads call was made and no real post was published.

### Review follow-up on PR-2: two confirmed risks, both closed before merge

A pre-merge review of PR-2 raised two specific questions about the claim/`'publishing'` design above; both were confirmed real and fixed in the same PR, with no new table/service/mechanism:

**Risk A — a plain PATCH could still cause a duplicate.** Point 6 above originally also allowed `PATCH /api/social-publications/[id]` to move a `'publishing'` row to `'failed'` or `'published'` directly — the idea being that only a human who'd confirmed the real outcome on the platform would do that. That reasoning doesn't hold: this generic PATCH endpoint has no way to tell "this row is genuinely stuck" apart from "a send is actively in flight right now, under the claim that's running this exact moment" — both look identical from outside (`status = 'publishing'`). If ANY caller — a stray click, a stale tab, a script — PATCHes `status: 'failed'` while the real send is still genuinely running, the row leaves `'publishing'` and immediately re-satisfies `claimPublicationForSending`'s `WHERE status NOT IN ('publishing', 'published')`: a second, fully independent claim can succeed and call the platform's send API a second time WHILE the first is still in flight — a real duplicate post, the exact thing the atomic claim exists to prevent. Fixed: `isForbiddenPublicationStatusTransition` now forbids EVERY transition away from `'publishing'` through this endpoint, not just `→ ready`. The only way a `'publishing'` row ever changes status again is the publisher's own internal final write (its claimed attempt actually finishing) — there is no in-app recovery path left at all for a row that's genuinely, permanently stuck (its claiming process crashed and nothing will ever write a final result); that now requires a direct database operation by someone who has independently confirmed the real outcome on the platform itself, the same as any other rare operational incident — an explicit, accepted trade-off, not an oversight.

**Risk B — a response-body read failure was indistinguishable from a confirmed rejection.** Each publisher's send-call handling read `const data = await res.json().catch(() => null)` — this swallows a body-STREAM error (the connection drops mid-stream, after the 2xx status line and headers already arrived) exactly the same way it swallows a harmless JSON-syntax error, both landing on `data = null`. The existing `if (!res.ok || !data?.ok)`-shaped check then reads that as "Telegram/VK/Instagram/Threads rejected this" and wrote `status = 'failed'` — even though a 2xx status means the platform almost certainly accepted (and, for these four platforms' send endpoints, actually posted) the content; we just couldn't read the confirmation body. A `'failed'` row doesn't trip the "already published" 409/claim guard, so a next retry would call the platform's send API again for something that may have already gone out — a real duplicate post. Fixed in all four publishers: the send call's own response body is now read separately from the ok/rejection check, with its own `bodyReadFailed` flag; a 2xx response whose body fails to read now sets `sendOutcomeUnknown` (the same flag already used for the send call's own `fetch()` throwing outright) instead of writing `'failed'` — the row stays `'publishing'`, a `503` is returned, and it is never auto-retried (same path as any other unconfirmed outcome). A non-2xx response is still a confirmed rejection regardless of whether its own body can be read — nothing was posted either way, so `'failed'` there remains correct and safe to retry.

CRM preparation for attribution identifiers. **DriveSet is not changed in A1**: the old DriveSet keeps sending leads exactly as before, and the new fields stay empty until DriveSet Capture A2 sends them. - **New `leads` columns (all nullable):** `lead_tracking_id TEXT`, `metrika_client_id TEXT` (text on purpose: Metrika ClientID is a UInt64 of up to 20 digits and can exceed the JS safe-integer range — it is never converted to a number), `yclid TEXT`, `first_seen_at TIMESTAMPTZ`. **Index:** one partial unique index `leads_lead_tracking_id_uidx ON leads (lead_tracking_id) WHERE lead_tracking_id IS NOT NULL`; no index on `metrika_client_id`/`yclid` (joins read a period-bounded, project-scoped lead set already served by `leads_project_id_idx`; add one when a real lookup exists). A2 note: because a malformed *provided* value is rejected, DriveSet must validate and drop invalid optional attribution values itself instead of forwarding them.

- **Not in A1:** DriveSet changes, Direct changes (`ADD_METRICA_TAG` untouched), Metrika API, `_ym_uid` / `getClientID`, localStorage, `source` classification, `reachGoal` parameters, Logs API, unified analytics, AI, UI, writes.

- **`campaign.settings`** — always present, from the same single `campaigns.get` (no extra request): `timeZone`, `currency`, `endDate`, `dailyBudget{amount,mode}`, `negativeKeywords[]`, `negativeKeywordSharedSetIds[]`, `counterIds[]` (Metrika counter ids configured in the campaign — ids only, Metrika itself is not read), `strategy{search,network}` each `{type, weeklySpendLimit, bidCeiling, budgetType}` (rubles; the values live in the sibling object named after the strategy type), `options{OPTION: YES/NO}`. Requested for both `TextCampaignFieldNames` and `UnifiedCampaignFieldNames` (Direct returns the matching one). Field names were taken from Direct's own answers (`direct_api_reference`, enum errors) and from a real read of the DriveSet campaign. Note: that read (through AdCab, default API version v5) reported the campaign as `TEXT_CAMPAIGN` with a `TextCampaign` block, while the production Observer (`json/v501`) reports `UNIFIED_CAMPAIGN`; `campaign.settings` is built from either block (`TextCampaign` or `UnifiedCampaign`), so both work.
- **`structure`** — only with `GET …/observer?structure=1` (or `true`; any other value → 400). Opt-in so v0.1 callers keep the same 3 Direct requests: `adGroups[]` (`id, campaignId, name, status, servingStatus, type, regionIds` — ad groups have **no `State`** field in Direct, only `Status` + `ServingStatus`; geo is therefore per ad group, not per campaign), `adGroupsTruncated`, `keywords{items[], truncated}` (`id, adGroupId, campaignId, keyword, isAutotargeting, state, status, servingStatus, bid, contextBid, strategyPriority`, rubles; autotargeting is the pseudo-keyword `---autotargeting` and additionally carries `autotargeting{searchBidIsAuto, categories[], brandOptions[]}`), `negativeKeywords{campaign[], campaignSharedSetIds[], adGroups[{adGroupId, phrases[], sharedSetIds[]}]}` — so an agent can answer "is this phrase already excluded, and where". Minus-words written inside a keyword phrase (`-москва`) stay part of `keyword`; shared negative-keyword **sets** are returned as ids only.
- **Direct methods added (fixed in the client, never taken from the request):** `adgroups.get` and `keywords.get` — both `get` only. Selection is always `CampaignIds: [<allow-listed id>]` (never `Ids`/`AdGroupIds`/`KeywordIds` from outside) and rows of any other campaign are dropped. Mutations (`add`, `update`, `delete`, `suspend`, `resume`, `setAuto*`, …) and every other service stay unrepresentable. Request count with `structure=1`: `campaigns.get` + `adgroups.get` + `keywords.get` (+ the two reports), no per-object calls. Lists are paged (`Page.Limit` 2000, up to 5 pages via `LimitedBy`); beyond that the cap is reported separately: `adGroupsTruncated=true` (ad group list, and with it the ad-group part of `negativeKeywords`, is incomplete) and `keywords.truncated=true` (keyword list only).
- **Failure policy:** if a requested structure read fails the whole request fails with the normalised Direct error (same kinds/HTTP mapping as v0.1) — a negative-keyword check must never be answered from a half-read structure. Without `structure` nothing changes from v0.1.
- Not in v0.2 (next small PRs): ads (`ads.get` — several ad types), sitelinks/extensions, contents of shared negative-keyword sets (`negativekeywordsharedsets.get`), keyword/ad statistics.

Known test traffic is excluded from `metrika.excludingTest`, `funnel.excludingTest`, the CRM Direct count and `crm.byStatus`; raw totals (`metrika.visits`, `funnel.*`, `crm.leads`) stay equal to the Metrika/CRM Observers. This is the site's first-touch UTM — **AGGREGATED/PROBABLE, not proof of a click**. `crm.leadsUnattributed` = the rest of the non-test leads. No `possibleDuplicates`, no `qualifiedLeads` (the CRM has statuses but no objective quality rule; `crm.byStatus` is a plain split).

Direct money is RUB **including VAT** (`IncludeVAT=YES`). Every derived metric is `{value, reason?}`; `cpl` also carries `attributionConfidence:'AGGREGATED'`.
- **Formulas:** `clickToVisitPct = Metrika directClickVisits / Direct clicks`; `visitToQuizPct = quizStartVisits / visits`; `quizToContactPct = quizPhoneVisits / quizStartVisits` (`quizPhone` fires when the contact step opens); `visitToMetrikaLeadPct = leadSubmitVisits / visits`; `visitToCrmLeadPct = crm.leadsDirect / directClickVisits`; `clickToCrmLeadPct = crm.leadsDirect / clicks`; all ×100, 2 decimals. All-traffic percentages use the test-excluded values when the test segment was read (`conversions.basis = excluding_test`, otherwise `raw`). **`cpl = direct spend / crm.leadsDirect` only when** the period is complete, Direct and CRM answered, spend > 0, the CRM list is not truncated and `leadsDirect ≥ 1`; otherwise `null` with `period_incomplete` / `direct_unavailable` / `crm_unavailable` / `no_spend` / `crm_truncated` / `no_attributed_leads` — never a fake zero. A zero denominator gives `no_clicks`, `no_visits`, `no_quiz_starts` or `no_direct_visits`. `low_volume` (clicks < 100 or Direct CRM leads < 5) only warns.
- **Breakdowns:** `campaign` EXACT by id; `autotargeting` and `searchQueries` AGGREGATED (the Metrika autotargeting row is recognised by `lastDirectPhraseOrCond` id `11.0` or the exact normalised name `Автотаргетинг`/`Autotargeting`; Direct numbers exact; Metrika visits joined by normalised phrase text; CRM `NOT_SAFE`; top 50 queries by spend); **no query-level CPL**. `daily` merges Direct, Metrika and CRM by Moscow day with zero fill (CRM per day excludes known test leads; Metrika per-day columns are raw).
- **Contact intents** (`telegram`, `max`, `phone` visits with the goal) are separate signals, never summed or counted as leads; a visit may trigger several. They are also given for the Direct-click segment. They are not linked to CRM leads.
- **Failure policy:** each source is `ok` / `partial` / `unavailable` (`meta.sources`); one failing never fails the others; dependent metrics are `null` + reason and a warning is added. HTTP 200 if any source answered; 502 if all failed; 503 if all are unavailable because nothing is configured; 400 invalid project/period; 404 unknown project. Direct and Metrika are cut at a 50 s deadline (`timeout`); the CRM query is awaited as is, never aborted by the deadline. Concurrency makes the latency ≈ the slowest source (Direct reports can poll for readiness). No cache.
- **Attribution (stated in the response):** Direct → Metrika = campaign matched EXACTLY by id, visits AGGREGATED (clicks and visits are different populations); Metrika → CRM = AGGREGATED (first-touch UTM vs last-significant-source); overall AGGREGATED. The funnel is visits that reached each goal, not a proven same-visit sequence.
- **Privacy:** aggregates only; no name, phone, contact, email, ClientID, yclid or lead_tracking_id anywhere in the response (a test injects such values into every source fixture and asserts they never appear).
- **Not in v0.1:** AI, UI, cron, cache, DB, Logs API, ClientID verification, query-level CRM attribution, duplicate detection, `qualifiedLeads`, multi-client onboarding.
- **NEEDS VERIFICATION after production deploy:** Direct Reports accepting `DateTo = today` and its current-day lag; the Direct-scoped goal metrics for all funnel goals; the test-traffic counts; the filter syntax of the test segment (a rejection shows as warning `extras_unavailable`); CRM `yandex/ya` + campaign mapping on the first real advertising lead (the last 7 days had none, so `cpl = null / no_attributed_leads` is expected); latency through admin.olnoo.com.

### Direct Agent — MVP HARD MODE (approved plan; not built yet)

**Goal of the first working scenario:** read search queries → deterministic detector → AI explanation → negative-keyword proposal → human confirmation → manual apply first, Hand v1 later → re-read → verify. The scenario is "found a bad search query → explained → proposed a negative phrase".

**Already exists and is reused (do not rewrite without a concrete blocker):** Direct Observer (read-only client, search queries, keywords, campaign/group negative keywords, campaign/group structure — `?structure=1`), Metrika Observer, CRM Observer, Unified Analytics, REAL/TEST/UNKNOWN classification, MCP summary (`get_driveset_summary`).

**At most 3 PRs:**

3. **Hand v1** — only if the Detector produced useful proposals the owner agrees with. - Test Traffic must be activated on production (`DRIVESET_TEST_CLASSIFICATION_SINCE` set, see "Test Traffic v1") before REAL/TEST/UNKNOWN is used for product conclusions; until then every non-marker lead is UNKNOWN and CPL is `null`.

### How Telegram comments actually work (researched before building this — do not assume otherwise)

A channel's comments are **not** part of the channel itself. Enabling "Discussion" on a channel links it to a separate, ORDINARY (never a forum/topics-enabled) **supergroup** — confirmed against Telegram's own discussion-groups documentation: "the comment section of a channel post is simply the message thread of the automatically forwarded channel message." Every channel post is auto-forwarded into that group as an ordinary message (`is_automatic_forward: true`), and every viewer comment is a plain `message` in that same group threaded to that one auto-forwarded copy. `message_thread_id` is only unique **within one chat** — never globally — so a comment event alone never says which project it belongs to; it has to be resolved through which `social_publications` row owns that specific `(chat_id, thread_id)` pair.

- **Forward origin (review fix):** the forward's own channel/post identity is read from `forward_origin` (`MessageOriginChannel` — `chat` + `message_id`), the CURRENT shape since Bot API 7.0 (29 Dec 2023). Telegram still sends the legacy `forward_from_chat`/`forward_from_message_id` fields too (its own stated back-compat policy), so `lib/social-telegram-comments.ts` reads `forward_origin` first and falls back to the legacy fields only if it's absent — never the other way round, and never only the legacy shape, which would silently stop working once Telegram eventually retires it.
- **Thread-id detection does not assume every comment carries `message_thread_id` (review fix):** a reply directly to the auto-forwarded post, or a reply to another comment, can in principle omit it; `lib/social-telegram-comments.ts` falls back to `reply_to_message` — anchoring on the root's own id when `reply_to_message.is_automatic_forward` is true, or inheriting `reply_to_message.message_thread_id` otherwise. Nested replies (a reply to a reply) still resolve to the SAME thread root this way, since Telegram keeps `message_thread_id` constant for the whole thread regardless of depth — no forum-topic special-casing needed. A `message_thread_id` that happens to belong to an unrelated native forum topic (if the discussion group ever had Topics enabled for its own, unrelated reasons) is harmless even though this file can't distinguish it from a real comment thread: `resolveThread` only ever matches a `(chat, thread)` pair it already recorded from a genuine auto-forward, so an unrelated topic id simply matches nothing and the message is dropped as unattributed — never misattributed to the wrong post or project.

A bot only receives these group messages at all if it is a **member of the discussion group** and either (a) added as an **administrator** there (bypasses privacy mode entirely), or (b) has privacy mode disabled via `@BotFather` → `/setprivacy` (then removed and re-added to the group for the change to take effect). Being merely an admin of the **channel** is not enough — the discussion group is a separate chat with its own membership.

### Schema

Migration `db/migrations/0023_social_comments.sql` (additive, idempotent, **applied to production**):
- `social_publications.telegram_discussion_chat_id` / `telegram_discussion_thread_id` (TEXT, default `''`) — **learned reactively, never configured by hand.** Stamped onto a publication row the first time its own auto-forward event is observed (see `linkAutoForward` below); empty until then. A partial unique index on `(telegram_discussion_chat_id, telegram_discussion_thread_id)` guards against two different publications ever claiming the same thread.
- `social_comments` — one row per distinct Telegram comment: `project_id`, `social_publication_id` (nullable, `ON DELETE SET NULL` — deleting the post never deletes its comment history), `platform` (`'telegram'` for now), `external_comment_id`, `author_name`, `author_username`, `body`, `external_posted_at`, `notified_at`, `created_at`. Unique index on `(project_id, platform, external_comment_id)` — the dedup key: a webhook redelivery, or this app's own retry after a transient failure, can never create a second row for the same real comment.

Migration `db/migrations/0024_social_telegram_pending_auto_forwards.sql` (additive, idempotent, **applied to production** — see "Race fix" below for why it exists):
- `social_telegram_pending_auto_forwards` — a short-lived rendezvous table, NOT a second source of truth for the (chat, thread) mapping (that stays `social_publications`' own two columns). One row per `(discussion_chat_id, thread_id)`: `forward_from_chat_id`, `forward_from_chat_username`, `forward_from_message_id`, `created_at`. Rows are deleted the moment they're resolved, and opportunistically pruned after 7 days on every new insert (no new timer — inline cleanup).

Migration `db/migrations/0025_social_telegram_pending_comments.sql` (additive, idempotent — see "Residual race fixed" below):
- `social_telegram_pending_comments` — same short-lived-rendezvous role as the table above, for a comment instead of an auto-forward: one row per `(discussion_chat_id, thread_id, external_comment_id)`, holding the comment's own fields (`author_name`, `author_username`, `body`, `external_posted_at`). Deleted the moment its thread links and the comment is replayed into `social_comments`; opportunistically pruned after 7 days on every new insert.

### Project isolation, without a per-client registry

No new "which chat belongs to which project" table for the actual (chat, thread) mapping. Two **already-existing, already-verified** facts resolve it entirely: (1) `social_accounts.username` is the project's own real, Bot-API-confirmed Telegram channel identity (see "Telegram channel connection" above); (2) `social_publications.external_post_id` is the exact Telegram message id a post was published with (`lib/social-telegram.ts`). An auto-forward event carries both the channel's identity and that same message id, so matching against these two existing columns — never a new mapping — is enough to say which project a discussion thread belongs to, and the lookup is naturally scoped to one project's own data; a project's comments can never be attributed to another project's channel.

**Normalization fix:** `social_accounts.username` can legitimately hold any of three equivalent-looking but textually different forms — a bare handle (`olnoo_channel`), the canonical `@handle` form (`lib/social-accounts-telegram-connection.ts`'s `canonicalChatIdentifier` writes this one when the channel has a public username), or a raw numeric chat id (written instead for a channel with no public username). An earlier version of `linkAutoForward` normalized only the webhook's own candidate values before comparing them against the raw stored `social_accounts.username` column in SQL — so a row stored as a bare handle (no `@`) would never match a webhook's always-`@`-normalized candidate. `findAccountForChannel` (`lib/social-comments.ts`) now normalizes **both sides** through `telegramIdentifiersMatch` (`lib/social-telegram-verify.ts`) before comparing, in application code rather than SQL (the account list is small — one row per project's connected Telegram channel — so this is simpler and equally correct). Covered by `lib/social-telegram-verify.test.ts` and `lib/social-comments.test.ts`.

### Race fix — the webhook arriving before the publish call commits `external_post_id` (confirmed production bug)

**Root cause, confirmed in production:** a real publication (`external_post_id = 8`) had `telegram_discussion_chat_id`/`telegram_discussion_thread_id` both stuck at `''`, and zero comments ever appeared for it, despite the webhook, bot permissions and schema all being correctly in place (see "Confirmed in production" above). `lib/social-telegram.ts`'s `publishSocialPublicationToTelegram` calls Telegram's `sendMessage`, then — only after that HTTP call returns — writes `external_post_id` to the row. Telegram, however, auto-forwards the newly-posted channel message into its discussion group (and calls this app's webhook for that forward) as part of posting the message itself — this can easily arrive at `/api/telegram/comments-webhook` and be processed by the OLD `linkAutoForward` **before** the publish call's own `sendMessage` response comes back and the `external_post_id` UPDATE commits. The old `linkAutoForward` matched purely against the already-committed `external_post_id`; losing this race meant the auto-forward event found no publication row to stamp and was silently dropped forever — no retry, no error, just permanently unlinked.

**Fix (no new service, timer, or queue — reuses Postgres, per the task's own constraint):** `linkAutoForward` (`lib/social-comments.ts`) now has two outcomes when it can't yet find a matching publication: the channel itself is unknown (nothing to do), or the channel IS known but no publication has this `external_post_id` **yet** — the latter case is recorded in the new `social_telegram_pending_auto_forwards` table instead of discarded. `resolvePendingAutoForwardForPublication` (same file) is called from `lib/social-telegram.ts` immediately after its own success `UPDATE` commits `external_post_id` — it looks for exactly this pending event (matched by message id + channel identity, via the same `telegramIdentifiersMatch` normalization) and, if found, stamps the thread onto the just-published row and deletes the pending row. This makes linking succeed **regardless of which side — the webhook or the publish call — commits first**, with the resolution running inline on whichever side arrives second. A failure resolving a pending event never affects the publish result itself, which has already fully succeeded by that point (same contract as `lib/social-comment-notify.ts`'s own never-throw notifications). Covered end-to-end (webhook before commit, then the publish committing, then a new comment resolving) by `lib/social-comments.test.ts` and `lib/telegram-comments-webhook-flow.test.ts`.

**Known limitation, stated plainly:** this fix is forward-looking. A publication whose auto-forward event was already lost BEFORE this fix shipped (like the real `external_post_id = 8` row found in production) cannot be retroactively repaired — Telegram has no replay mechanism for a historical webhook event, and the only way to produce a new one would be re-forwarding the post, which creates a second, different discussion-group message and would not restore continuity with whatever comments (if any) already exist on the original thread. Any publication made before this fix, with an empty `telegram_discussion_chat_id`, stays permanently unlinked; every publication made after it self-heals regardless of event order.

### Residual race fixed (review finding on the race-fix PR) — a Postgres advisory lock, and comments arriving before the link completes

**The finding:** `linkAutoForward`'s "check the publication, if absent write a pending row" and `resolvePendingAutoForwardForPublication`'s "check the pending table, if present act on it" were each individually correct, but — as two separate, otherwise-unsynchronized statements — could still interleave across the two: (1) `linkAutoForward` checks for the publication, absent; (2) the publish call commits `external_post_id`; (3) `resolvePendingAutoForwardForPublication` checks the pending table, ALSO absent, because step 1 hasn't written it yet; (4) `linkAutoForward` (only now) writes the pending row — too late, nothing ever looks for it again. The event is lost exactly as before the first fix, just with a narrower window.

**Fix — `pg_advisory_xact_lock`, no new service/timer, correct under any transaction order:** both functions now run their whole "check, then maybe act" sequence inside one Postgres transaction holding an advisory lock (`lib/social-comments.ts`; same mechanism as `lib/telegram-business-lead.ts`'s `findOrCreateTelegramLead` and `lib/social-accounts-telegram-connection.ts`'s connect guard), keyed by `` `tg-autofwd:${projectId}:${externalPostId}` ``. Because both sides acquire the SAME key before doing anything else, whichever side's transaction starts first now runs its entire check-then-act atomically before the other side's own check can even begin — there is no longer a gap in which the second side can observe a stale "not there yet" state for something the first side is mid-write on. This holds for the reconciliation regardless of which of the two actually wins the lock on a given run — proved by a dedicated concurrency test (`lib/social-comments.test.ts`) that runs both functions concurrently through real, independent Postgres connections and asserts the decisive fact (`resolveThread` shows the thread linked afterwards), not merely that neither call threw.

**The same category of gap, one level down — comments:** the exact same kind of race applies to a comment arriving in the window before its thread is linked: `resolveThread`'s own check ("is this thread linked yet") and the stamp-the-thread step (inside `linkAutoForward`/`resolvePendingAutoForwardForPublication`) could race the same way, and a comment lost there is unrecoverable — `comment_unattributed` is a handled (200 OK) outcome, so Telegram never redelivers it. Fixed with a SECOND, independent advisory lock keyed by `` `tg-thread:${discussionChatId}:${threadId}` ``, held by: `resolveThread`'s own check-or-remember step, AND the stamp-the-thread step in both `linkAutoForward` and `resolvePendingAutoForwardForPublication` (acquired right before stamping, nested inside the first lock where both are held — independent keys, same transaction, released together at commit). `resolveThread` takes an optional 4th argument, the raw comment event: if the thread isn't linked yet, the comment is stored in the new `social_telegram_pending_comments` table (migration `0025_social_telegram_pending_comments.sql`) instead of being dropped. The moment a thread IS stamped, `replayPendingComments` (`lib/social-comments.ts`) inserts every comment waiting for that exact (chat, thread) pair into `social_comments` via the SAME `insertCommentIfNew` dedup path a live comment uses, leaving `notified_at` `NULL` — the EXISTING `listUnnotifiedComments`/`retryUnnotifiedComments` sweep (already run at the end of every webhook call) sends the notification on a later call, so no new notifier wiring was needed. The webhook call that originally saw the comment still correctly reports `comment_unattributed` for ITS OWN request (Telegram is never kept waiting or asked to redeliver) — the comment itself is delayed, never lost. Covered by `lib/social-comments.test.ts` (both orderings: `linkAutoForward` performing the stamp, and `resolvePendingAutoForwardForPublication` performing it; plus the "already linked" fast path that never touches the pending-comment table at all).

**Not changed:** the Publisher, nginx, the webhook secret/registration, CRM, Ads, SEO, GitHub Actions. No new service, queue, or timer — two new Postgres tables and application-level advisory locks, nothing else.

### Why a repeated "Publish" in the UI did not create a new `social_publications` row — investigated, confirmed NOT a defect

Requirement from this fix's task: confirm the cause before touching the Publisher, and don't change it without a confirmed defect. Finding: `ensurePublicationsForChannels` (`lib/social.ts`) is, by design, **the only place a publication row is ever created**, and it creates exactly one row per `(social_post_id, platform)` — never a second one for a channel the post already has a row for. `publishSocialPublicationToTelegram` (`lib/social-telegram.ts`) also explicitly refuses (`409`) to resend a publication whose `status` is already `'published'`, specifically to prevent posting the same content to the channel twice. So clicking "Publish" again on an already-published post correctly does nothing new — no new row, no second Telegram message — which is the intended duplicate-publish guard (requirement: "защита от повторной публикации"), not a bug. **No change was made to the Publisher.** The actual fix for the missing thread link is the race fix above, which requires no republish at all — it resolves automatically the moment the original publish call's own `external_post_id` commit and the webhook's auto-forward event have both arrived, in either order.

### AI-suggested replies to comments (MVP) — human-confirmed only, no auto-send

**Goal:** let an admin reply to a viewer's comment from inside Social → Comments, with the OLNOO AI Router suggesting a draft from the comment and its original post — never sent automatically, never inventing facts not present in either. Reuses the existing AI Router client and the existing posting bot; no new AI provider, no new Telegram bot, no new service/queue/timer.

- **Schema:** migration `db/migrations/0026_social_comment_replies.sql` — `social_comment_replies` (`id`, `project_id`, `social_comment_id`, `status` one of `sending`/`sent`/`failed`, `body`, `external_reply_message_id`, `error`, timestamps). **At most one row per comment, ever** (`UNIQUE` on `social_comment_id`) — this is not just a data-modeling choice, it IS the no-double-send mechanism (see below). A draft suggestion is never persisted — nothing is written to Postgres until a human clicks "Отправить"; "Предложить ответ"/"Сгенерировать заново" only ever call the AI Router and hand the text back to the browser.
- **Code:** `lib/social-comment-reply.ts` (DB-backed, `pool` injected, `@/`-free, same convention as `lib/social-comments.ts`): `getCommentForReply` (fetches the comment, its original post's text, its discussion chat id, and any existing reply row — all scoped by `project_id`, so a comment id from another project resolves as not-found, same guarantee as every other Social endpoint), `suggestCommentReply` (calls `lib/ai-router.ts`'s existing `callAiRouter` — the SAME client `lib/social-ai.ts` already uses for post-variant generation — with the ORIGINAL POST and the COMMENT as context; detects the reply language from the comment's own text, same Cyrillic heuristic as `lib/social-ai.ts`; never invents facts per its system prompt's hard rules; read-only, writes nothing), `sendCommentReply` (the only place in this feature that calls Telegram).
- **No double send, including under a double click or two concurrent requests — for BOTH a first-ever send and a manual retry:** `sendCommentReply` atomically claims this comment's one row before calling Telegram at all:
  ```sql
  INSERT INTO social_comment_replies (...) VALUES (..., 'sending', ...)
  ON CONFLICT (social_comment_id) DO UPDATE SET status = 'sending', ...
  WHERE social_comment_replies.status = 'failed'
  RETURNING id
  ```
  A fresh comment is claimed by the `INSERT` itself. A comment whose one row is already `'sending'` (unresolved) or `'sent'` (delivered) NEVER matches the `WHERE` clause, so the conflict is always silently discarded and the claim always fails — retry is categorically refused for both, by construction, not by a separate check. A comment whose row is `'failed'` (a CONFIRMED, definitive rejection) DOES match, so the `DO UPDATE` atomically flips it back to `'sending'` — **this is the one, and only, state a manual retry is ever allowed from** (review finding — see below). Postgres's row lock on the conflicting row serializes two concurrent retries the same way `claimPublicationForSending` (`lib/social-publication-claim.ts`) serializes the Social Publisher's own claim, one level down: whichever request's turn comes first wins; the other sees its own insert silently discarded (the winner already moved the row off `'failed'`) and is refused with `409` before any Telegram call. Proved by dedicated concurrency tests in `lib/social-comment-reply.test.ts` — both for the very first send and for a retry after a confirmed failure — asserting Telegram was called exactly once and exactly one row exists, never merely "no SQL error".
- **`reply_to_message_id` (requirement 6):** the reply is sent via Telegram's `sendMessage` into the comment's own discussion chat (`social_publications.telegram_discussion_chat_id`, resolved through the comment's `social_publication_id`), with `reply_to_message_id` set to the comment's own `external_comment_id` — a real Telegram reply to the specific comment, not a new top-level message. Covered by a dedicated test asserting the exact request body sent to Telegram's API.
- **Unknown Telegram outcome — never retriable, under any circumstance:** mirrors `lib/social-telegram.ts`'s own `sendOutcomeUnknown` handling exactly — a timeout or dropped connection (the fetch itself never got a response) is NOT written as `'failed'`; the row is deliberately left at `'sending'` and a `503` is returned. No code path anywhere ever moves a `'sending'` row forward on its own, and the atomic claim's own `WHERE status = 'failed'` clause means a human clicking retry can't move it forward either — a human must check Telegram directly before anything further happens to that row. `'sent'` is equally terminal — never retriable, by the same construction.
- **Review fix — a CONFIRMED failure IS now manually retriable (was: never, in the original MVP):** a definitive Telegram rejection (a response was received, just not success) is written as `status = 'failed'` with the error. The original MVP treated this as terminal, same as a stuck `'sending'` row — review found that conflates two different things: an outcome Telegram never confirmed one way or the other (genuinely unsafe to retry blindly) versus an outcome Telegram explicitly and definitively rejected (safe to retry once the admin fixes whatever Telegram complained about, e.g. edits the text). The atomic claim above now allows exactly this one case, and only this one, back into `'sending'` — the UI's "Повторить" button re-opens the SAME edit-and-confirm flow a fresh suggestion uses (pre-filled with the failed attempt's own text), never an instant silent resend. The API/route layer is unchanged: a `'failed'` row is still returned as the `social_comment_replies` row itself (HTTP 200, same convention `app/api/social-publications/[id]/publish-telegram/route.ts` already uses for the Social Publisher) — the row's own `status`/`error` fields, never the bare HTTP status, are what the UI must inspect, and `components/sections/social-comments-view.tsx` does exactly that (a `'failed'` row is rendered as a clear error + a retry button, never as a sent reply).
- **API:** `POST /api/social-comments/[id]/suggest-reply?project=<slug>` (read-only, returns `{ reply }`), `POST /api/social-comments/[id]/send-reply?project=<slug>` (body `{ text }`, returns the `social_comment_replies` row — used for both a first send and a manual retry, same endpoint). Both project-scoped like every other Social Community endpoint; access control is the SAME external nginx layer already covering `/api/social-comments` — neither route was added to any exemption list (requirement 9: reuse the existing Admin authorization, no nginx change).
- **UI:** `components/sections/social-comments-view.tsx` gained a "Reply" column — "Предложить ответ" → an editable textarea with "Сгенерировать заново" / "Отправить" / "Отмена" (nothing is sent until "Отправить" is clicked) → once sent, the row shows the actual sent text (`status = 'sent'`); `'failed'` shows the error plus a "Повторить" button that re-opens the same edit-and-confirm flow, pre-filled with the failed text; `'sending'` (unresolved) shows a plain "check Telegram directly" message with no retry affordance of any kind. `listCommentsForProject` (`lib/social-comments.ts`) now LEFT JOINs `social_comment_replies` so the whole list loads in one request.
- **Not in this MVP:** auto-replies/automatic sending of any kind (every send, including a retry, is one explicit human click), a retry/resend affordance for a stuck `'sending'` row (same stated limitation as the Publisher's own stuck-`'publishing'` rows — only a `'failed'` row is ever retriable), editing or deleting an already-sent reply, replying to a reply (threaded conversation beyond one reply per comment), any platform other than Telegram, a CRM lead from a reply.

### Webhook vs. polling — why webhook, and why this doesn't conflict with anything

Requirement weighed explicitly: `getUpdates` and `setWebhook` are mutually exclusive for one bot (setting one disables the other), and `getUpdates` additionally has no safe way to run from more than one independent consumer — each marks updates "read" by advancing a shared offset, so two independent pollers lose events between them. **Webhook was chosen**: `TELEGRAM_BOT_TOKEN` had neither a webhook nor any `getUpdates` polling registered anywhere before this change (confirmed above), so there is nothing to conflict with — this is the bot's first and only webhook registration, mirroring `/api/telegram/business-webhook`'s own pattern (a *different* bot/token) exactly.

- Route: `POST /api/telegram/comments-webhook` (`app/api/telegram/comments-webhook/route.ts`) — wires the real DB pool into `lib/telegram-comments-handler.ts`'s `handleTelegramCommentsUpdate`, kept free of `@/` imports (same reasoning as `lib/telegram-business.ts`) so it runs directly under `node --test` with fake deps. Auth: header `X-Telegram-Bot-Api-Secret-Token` compared in constant time to `TELEGRAM_COMMENTS_WEBHOOK_SECRET` (a new env var; unset → 503, wrong secret → 401).
- `lib/social-telegram-comments.ts` (pure): classifies one Telegram update as `auto_forward`, `comment`, or `ignore` — never guesses (edits, non-message updates, the bot's own messages, and messages with no thread at all are all `ignore`).
- `lib/social-comments.ts` (DB-backed, `pool` injected, `@/`-free): `linkAutoForward` (resolves + stamps the thread mapping, idempotent, records an unmatched-but-known-channel event as pending rather than dropping it — see "Race fix" above), `resolvePendingAutoForwardForPublication` (the publish side's half of that fix), `resolveThread` (optionally remembers an unattributed comment, see "Residual race fixed"), `replayPendingComments` (internal — inserts every comment a thread's stamp just unblocked), `insertCommentIfNew` (the dedup insert, `ON CONFLICT ... DO NOTHING` — atomic under concurrency by construction, no advisory lock needed for the insert itself), `listCommentsForProject`. `linkAutoForward`/`resolvePendingAutoForwardForPublication`'s own check-then-act sequences, and `resolveThread`'s, each run inside a `pg_advisory_xact_lock`-guarded transaction (see "Residual race fixed" — two keys, `autoForwardLockKey`/`threadLockKey`). Both `linkAutoForward` (on `thread_unknown`) and `resolveThread` (on `comment_unattributed`) log a diagnostic `console.warn` with only chat/thread/message ids and project/publication ids — never a comment's `author_name`, `author_username`, or `body`, and never any token.
- `lib/social-comment-notify.ts` — reuses the EXISTING owner-notification mechanism (requirement: "используй существующий механизм уведомлений, если он подходит"): same `TELEGRAM_BOT_TOKEN`/`CRM_NOTIFY_TELEGRAM_CHAT_ID` `sendMessage` pattern as `lib/lead-notify.ts`, no new env var for the notification itself. Called **at most once per genuinely new comment** — `handleTelegramCommentsUpdate` only calls it immediately after `insertCommentIfNew` reports a real insert, never for a redelivered/duplicate update. Never throws; a Telegram API failure here is logged and swallowed, and never risks the comment row already committed before it runs (requirement: "ошибка Telegram API не приводит к потере уже полученных комментариев").
- **Notification durability (review fix) — a comment's notification is no longer silently lost forever on a transient Telegram error.** `notifyNewComment` now reports whether the send actually succeeded; the route only calls `markCommentNotified` (`social_comments.notified_at`) on a confirmed success — a failure (or `CRM_NOTIFY_TELEGRAM_CHAT_ID` missing at the time) leaves it `NULL`. At the end of every webhook call, the route also runs a small, bounded `listUnnotifiedComments` sweep (`lib/social-comments.ts`) and retries each one — **no new timer, queue, or service**: this piggybacks on the SAME request the webhook already received, which is "minimal fix, no separate infrastructure" as asked. One stated limitation: a channel with zero further activity never triggers another retry on its own, so a stuck notification waits for the next real comment; acceptable for this MVP's volume, and the same systemd-timer pattern `lib/social-meta-token-refresh-sweep.ts` already uses is the natural upgrade if that ever matters.
- A transient failure (DB error) returns 500 so Telegram redelivers; redelivery is always safe (the dedup insert, and the idempotent thread-link update, both tolerate it).

### UI

`Social → Comments` (`?screen=social-comments&project=<slug>`), `components/sections/social-comments-view.tsx` — read-only list (author, comment text, a link to the post if resolved, time), newest first. `GET /api/social-comments?project=<slug>` (project-scoped, no "All projects" mode — same deliberate simplicity as `/api/ads`). Renders its own `ProjectSelector`; choosing "All projects" shows a prompt rather than a cross-project list (unlike `/api/ads`'s own screen, which renders nothing at all for "all" with no way to switch back from within it).

- Scoping: the webhook's `business_connection_id` is compared (plain string equality) against `TELEGRAM_BUSINESS_DRIVESET_CONNECTION_ID`. A match and only a match reaches lead creation; the sender's username is never used for this decision. Telegram only ever delivers a given `business_connection_id` to the bot that owns that connection, so this comparison is the full security boundary — no `getBusinessConnection` Bot API round-trip is made.
- Fail closed: `TELEGRAM_BUSINESS_DRIVESET_CONNECTION_ID` unset/empty → every connection, DriveSet's included, stays `ignored` (same wording as Patch A's global disable). The var is never hardcoded in code.
