## Social

Source of truth: Postgres (`olnoo-admin`), table `social_posts`, `project_id → projects.id`. Live at `?screen=social-posts&project=<slug>`.

Confirmed API routes (`olnoo-admin`): `GET/POST /api/social` (list filtered by `?project=<slug>`, create), `GET/PATCH/DELETE /api/social/[id]` (all project-scoped — a post id from another project cannot be read, edited, or deleted by supplying a different project slug or vice versa).

Post fields (create/edit UI): Topic, Content (shared body), Channels (`telegram`/`instagram`/`threads`/`vk`), Publish date, Status, and an optional per-channel text override per selected channel. `category` is a legacy column still present in the table — no longer shown in create/edit, the Posts list, or search; existing rows keep whatever value they already had, and new rows never get one written. When `instagram` is a selected channel, an "Instagram image" upload control appears — always visible while Instagram is selected, independent of the "Different text per channel" toggle, since it's mandatory content for Instagram publishing (see Instagram autoposting below), not a per-channel text override. It uploads a JPEG (see Instagram image upload below) and auto-saves the resulting URL into `social_posts.instagram_image_url` immediately, without waiting for the post's own Save button.

Per-channel text: every selected channel uses the shared Content by default. The "Different text per channel" toggle (off by default; auto-enabled when opening a post that already has a real override) reveals a text field for each *currently selected* channel when on — an empty field there falls back to Content. Turning the toggle off and saving clears the per-channel overrides for the channels selected at that moment; Content itself is never touched, and a channel's override is left alone while that channel isn't currently selected.

"Generate variants" (post edit UI, shown once Content is non-empty and at least one channel is selected) calls the existing OLNOO AI Router (`lib/ai-router.ts`'s `callAiRouter`, the same client SEO clustering uses — no separate provider integration) via `POST /api/social/generate-variants` (`lib/social-ai.ts`, project-scoped through the same `resolveProjectId`; sends Topic, Content, the selected channels, and project name/domain as context). The output language is always detected from Content itself (`detectContentLanguage` — Cyrillic present means Russian, otherwise English); the UI's interface locale is never sent to this endpoint and never affects the generated language, only the app's own interface strings — a Russian Content on an English-locale screen (or vice versa) still generates in Russian. The AI Router returns JSON with one key per requested channel only — the server drops any other key even if the model returns one — and the client fills the matching per-channel fields, turns the toggle on, and stops: nothing is sent to the server until the user clicks Save. No autoposting; this only asks the Router for text.

Migration: `db/migrations/0005_social_posts.sql`. `instagram_image_url` added by `db/migrations/0008_social_posts_instagram_image.sql`.

Data layer: `lib/social.ts`, reuses `resolveProjectId` from `lib/crm.ts` — no separate project-resolution mechanism.

The old `olnoo` implementation (`app/admin/social/`, `app/api/admin/social/*`, SQLite `social_posts` table in `data/crm.sqlite`) has been removed from the `olnoo` repo; `/admin/social` (and subpaths) now redirect to `admin.olnoo.com`, the same way `/admin/crm` does. No delete endpoint existed in the old implementation; the current one has one.

### Publication tracking

Per-channel publication status for each post, table `social_publications` (`project_id → projects.id`, `social_post_id → social_posts.id` cascade-deleted with the post, `social_account_id → social_accounts.id` set null if the account is deleted, plus `external_url`, `external_post_id`, `published_at`, `error`). `status` one of `draft`/`ready`/`published`/`failed`. One row is auto-created (status `draft`) for each channel as it's selected on the post — always as a side effect of the post's `channels` being written (`updateSocialPost`/`createSocialPost` in `lib/social.ts`), never from reading the Publications list. Channels later deselected keep their existing row rather than being deleted.

API routes (`olnoo-admin`): `GET /api/social-publications?post=<id>&project=<slug>` (pure read — lists whatever publication rows already exist for the post; creates nothing), `PATCH /api/social-publications/[id]` (project-scoped; assigning a `social_account_id` is rejected with 400 if that account doesn't belong to the same project). Setting `status` to `published` sets `published_at` to now (if not already set); setting it to anything else clears `published_at`.

MVP UI: manual "Mark as published" (optionally with an external URL) and "Back to ready" inside the post's Publications block, for any platform that isn't one of Telegram, VK, Instagram, or Threads. Telegram, VK, Instagram, and Threads all have real automated posting (see below).

`social_publications` is the only source of truth for whether a post is actually published — `social_posts.status` cannot manually claim `published`. All the reconciliation and creation logic lives in `lib/social.ts` (`syncPostStatusFromPublications`, `ensurePublicationsForChannels`, `isFullyPublished`) so `lib/social-publications.ts` can import it without a circular dependency; `status` becomes `published` only once every currently selected channel has a `published` publication, and is demoted back to `ready` the moment that stops holding. Read paths are strictly read-only — `listPublicationsForPost` never writes anything, not even to create a missing publication row. Reconciliation runs only after an operation that actually changes state: a publication's status changes (`updateSocialPublication` in `lib/social-publications.ts`), or the post's own selected channels change (`updateSocialPost`/`createSocialPost` in `lib/social.ts`, which is also where missing publication rows get created — always as a side effect of channels being set, never of a read). `updateSocialPost` also rejects `status: 'published'` outright (400) if the resulting channel set isn't actually fully published yet, and `createSocialPost` rejects creating a post already published — the API enforces this, not just the UI's disabled dropdown option. The Post UI computes the same fully/partially-published/ready/draft summary live from `social_publications` (`components/sections/social-publications.tsx`, `summarizePublications`) — nothing new is stored for this, it's derived on every read.

Migration: `db/migrations/0007_social_accounts_publications.sql` (both tables). Applied to production.

### Telegram autoposting

MVP automated posting for Telegram only (VK/Instagram/Threads are untouched — still manual, see above). From the post's Publications block, a `telegram`-platform publication that isn't already `published` shows a "Publish to Telegram" button in place of the manual "Mark as published" button; other channels are unaffected.

`POST /api/social-publications/[id]/publish-telegram?project=<slug>` (`lib/social-telegram.ts`, project-scoped through `resolveProjectId` like every other route in this module) calls the Telegram Bot API's `sendMessage` directly (no separate provider service, unlike the AI Router) using a bot token read from the server-only env var `TELEGRAM_BOT_TOKEN` — never stored in Postgres or Git, never sent to the browser. `TELEGRAM_API_BASE_URL` is a second, non-secret env var (default `https://api.telegram.org`) that only exists so a non-production environment can point at a mock server for testing, the same role `AI_ROUTER_URL` plays for `lib/ai-router.ts`.

Text sent is `social_posts.telegram_text` if non-empty, else `social_posts.body`. The target chat is the `social_accounts` row linked via the publication's `social_account_id` if set (rejected with 400 if that account isn't itself a `telegram` account), else the project's first `active` `telegram` account (`ORDER BY created_at ASC`) — there is no per-post channel picker yet, one active Telegram account per project is assumed. `external_url` is built as `https://t.me/<account.username without a leading "@">/<message_id>`.

No schema change: this reuses `social_publications`' existing `status`/`external_post_id`/`external_url`/`published_at`/`error` columns, all already present in `0007_social_accounts_publications.sql`. On success the row is set to `status='published'`, `external_post_id` = Telegram's `message_id`, `external_url` as above, `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs same as any other publication write. On a Telegram API error (bad request, chat not found, network failure) the row is set to `status='failed'` with the message in `error` — this is not thrown as an HTTP error, the route still returns 200 with the row, so the existing UI's error display (`publication.error`) shows it directly; calling the endpoint again from `failed` is a normal retry (nothing marks it non-retryable). Calling the endpoint on a publication that is already `published` is rejected with 409 before any Telegram API call (duplicate-send protection); calling it on a non-`telegram` publication is rejected with 400. No scheduler or background job exists — this only ever runs synchronously from the button click.

### VK autoposting

MVP automated posting for VK only, built on the same pattern as Telegram autoposting above (VK/Telegram are now both automated; Instagram/Threads are untouched — still manual). From the post's Publications block, a `vk`-platform publication that isn't already `published` shows a "Publish to VK" button in place of the manual "Mark as published" button; Telegram's flow is unchanged.

`POST /api/social-publications/[id]/publish-vk?project=<slug>` (`lib/social-vk.ts`, project-scoped through `resolveProjectId` like every other route in this module) calls the VK API's `wall.post` (`POST https://api.vk.com/method/wall.post`, `from_group=1` so the post is published as the community, not as the token's own user) using an access token read from the server-only env var `VK_ACCESS_TOKEN` — never stored in Postgres or Git, never sent to the browser. Must be a community/group access token, or a user token with `wall,groups` scope obtained via VK's classic OAuth — a `vk2.a.*` token from the newer id.vk.com PKCE login flow cannot call `wall.post`. `VK_API_BASE_URL` is a second, non-secret env var (default `https://api.vk.com`) with the same role as `TELEGRAM_API_BASE_URL`/`AI_ROUTER_URL` — only for pointing a non-production environment at a mock VK API.

Text sent is `social_posts.vk_text` if non-empty, else `social_posts.body`. The target community is the `social_accounts` row linked via the publication's `social_account_id` if set (rejected with 400 if that account isn't itself a `vk` account, or isn't `active`), else the project's first `active` `vk` account (`ORDER BY created_at ASC`) — same one-active-account-per-project assumption as Telegram. That account's `username` (or, if empty, the last path segment of its `public_url`) becomes the VK `owner_id`: a numeric value (with or without a leading `-`) is used directly, anything else (a screen name like `olnoo_ai` or `club212959296`) is resolved server-side via VK's own `utils.resolveScreenName` at request time — no schema change to pre-store a numeric id. A screen name that resolves to `type: 'user'` (a personal profile, not a community) is rejected with 400. `external_url` is built as `https://vk.com/wall<owner_id>_<post_id>` (VK's own canonical permalink format, valid regardless of the community's short name).

No schema change: reuses the same `social_publications` columns as Telegram. On success: `status='published'`, `external_post_id` = VK's `post_id`, `external_url` as above, `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs. On a VK API error (`{"error": {"error_code", "error_msg"}}`) or network/resolve failure, the row is set to `status='failed'` with the message in `error`, leaving `external_post_id`/`external_url` untouched — not thrown as an HTTP error, so the route returns 200 with the row and the UI shows it via `publication.error`; calling the endpoint again from `failed` is a normal retry. Calling the endpoint on an already-`published` publication is rejected with 409 before any VK API call (duplicate-send protection); calling it on a non-`vk` publication is rejected with 400. No scheduler or background job — synchronous, on-demand from the button click only. Media/attachments are not supported yet — text-only posts.

### Instagram autoposting

MVP automated posting for Instagram only, via the Instagram API with Instagram Login (no linked Facebook Page needed) — same pattern as Telegram/VK autoposting above, but Instagram has no text-only post: every publish needs exactly one image. From the post's Publications block, an `instagram`-platform publication that isn't already `published` shows a "Publish to Instagram" button in place of the manual "Mark as published" button; Telegram/VK are unchanged.

`POST /api/social-publications/[id]/publish-instagram?project=<slug>` (`lib/social-instagram.ts`, project-scoped through `resolveProjectId` like every other route in this module) runs Instagram's content-publishing flow against `graph.instagram.com`: `POST /{INSTAGRAM_ACCOUNT_ID}/media` (image_url + caption) creates a media container, a short bounded poll (`GET /{container-id}?fields=status_code,status`, up to 5 attempts ~1.5s apart) waits for `status_code=FINISHED`, `POST /{INSTAGRAM_ACCOUNT_ID}/media_publish` (creation_id) publishes it, then `GET /{media-id}?fields=permalink` reads back the real `instagram.com/p/...` URL. Unlike Telegram/VK, the target account is **not** resolved from `social_accounts` — an Instagram Login access token is already scoped to one specific account, so the account id and token come from their own env vars, `INSTAGRAM_ACCOUNT_ID` and `INSTAGRAM_ACCESS_TOKEN` (server-only, never in Postgres/Git, never sent to the browser). `social_accounts` is still required as a connection guard (a project-scoped, `active`, `platform='instagram'` row must exist — linked via the publication's `social_account_id` if set, else the project's first active instagram account), but its `username` stays the real Instagram `@handle` for display, never a token or numeric id — the numeric account id lives only in `INSTAGRAM_ACCOUNT_ID`. `INSTAGRAM_API_BASE_URL` is a third, non-secret env var (default `https://graph.instagram.com`) with the same role as `TELEGRAM_API_BASE_URL`/`VK_API_BASE_URL`.

Caption is `social_posts.instagram_text` if non-empty, else `social_posts.body` — same fallback pattern as Telegram/VK. The image is `social_posts.instagram_image_url` — populated by the upload control described below, mandatory: publishing is rejected with 400 if it's empty, since Instagram has no text-only post. This is the one schema change autoposting has needed so far (Telegram/VK's own platforms both support text-only posts, so they didn't): `db/migrations/0008_social_posts_instagram_image.sql` added `social_posts.instagram_image_url TEXT NOT NULL DEFAULT ''`.

On success: `status='published'`, `external_post_id` = the published media id, `external_url` = its permalink, `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs. On any failure — a Meta API error at container creation or publish, the container reporting `status_code=ERROR`/`EXPIRED`, the bounded poll timing out, or a network failure — the row is set to `status='failed'` with the message in `error`, leaving `external_post_id`/`external_url` untouched; not thrown as an HTTP error, so the route returns 200 with the row and the UI shows it via `publication.error`; calling the endpoint again from `failed` is a normal retry. Calling the endpoint on an already-`published` publication is rejected with 409 before any Instagram API call (duplicate-send protection); calling it on a non-`instagram` publication is rejected with 400. No scheduler or background job — synchronous, on-demand from the button click only. No carousel/Reels/video — single image + caption only.

### Instagram image upload

`social_posts.instagram_image_url` is populated by an upload control in the post edit UI (not manual text entry) — `POST /api/social/upload-instagram-image?project=<slug>` accepts one JPEG (`multipart/form-data`, field `file`), validates it (content-type plus a magic-byte check for the JPEG marker `FF D8 FF`, max 8MB — matching Instagram's own JPEG limit), and rejects anything else with 400. On success the file is written to disk under `<repo>/uploads/instagram/<project-slug>/<crypto.randomUUID()>.jpg` (original filename is never used, so there's no user-controlled path segment) and the route returns the absolute URL `GET /api/social/instagram-image/<project>/<filename>` serves it from — the client immediately PATCHes that URL into `instagram_image_url` (`components/sections/social-view.tsx`'s `handleImageUpload`), the same way the Publish buttons auto-save their own result, rather than waiting for the post's general Save button.

No S3/R2/new storage service, no Nginx/systemd change, no base64 in Postgres, no heavy media in Git (`uploads/` is gitignored). The uploaded file is **not** served through Next's `public/` folder convention — a root-level static request in this Next.js version collides with the `app/[locale]` dynamic segment and 404s before the file is ever checked (confirmed by direct testing: even a file present at build time under `public/` returned 404 the same way an unmatched locale does). So it's served instead by an explicit route handler, `GET /api/social/instagram-image/[project]/[filename]` (`lib/social-instagram-uploads.ts` holds the shared storage-path constant and the strict allow-list regexes both routes validate against — a numeric-UUID-shaped filename and a lowercase-alphanumeric-hyphen project slug — so a path-traversal attempt can never reach the filesystem call), which reads the file itself and returns it with `Content-Type: image/jpeg` and a long immutable `Cache-Control` (safe since filenames are fresh, never-reused UUIDs). `PUBLIC_SITE_URL` (non-secret env var, default `https://admin.olnoo.com`) turns the saved file into the absolute HTTPS URL Instagram's API needs to fetch it from — same non-secret-override role as `TELEGRAM_API_BASE_URL`/`VK_API_BASE_URL`.

This relies on OLNOO Admin running as a single server process with a persistent filesystem (confirmed: one systemd service, one port, no load balancer) — uploaded files live on that one server's disk. `git reset --hard origin/main` in the deploy workflow does not touch untracked files, so uploads survive a deploy. If the app is ever horizontally scaled, this would need real object storage instead. No cleanup job for orphaned files (e.g. after replacing an image or deleting a post) — out of scope for this MVP.

Before the file is written to disk, it's passed through `lib/social-instagram-image-normalize.ts` (`normalizeInstagramImageBuffer`) to guarantee an Instagram Feed-valid aspect ratio and max width — see "Instagram image aspect ratio normalization" below. That step doesn't add a new dependency on storage or a media service; it's a synchronous in-process transform using `jimp` (a pure-JS image library — no native binary, so nothing new for the KZ deploy's `npm ci` to compile), same request, same route, same disk.

### Instagram image aspect ratio normalization

Root cause this fixes: `lib/social-instagram.ts`'s `publishSocialPublicationToInstagram` (untouched by this) was rejecting real posts with Instagram's own `"The aspect ratio is not supported."` error, and separately, large images (e.g. 4000-6000px wide) with an already-valid ratio were failing to publish at all — the upload step accepted any JPEG shape/size. Instagram's Content Publishing API for Feed images only accepts an aspect ratio between **4:5 (portrait) and 1.91:1 (landscape) inclusive**, and a width of at most **1440px** (confirmed against Meta's current `developers.facebook.com/docs/instagram-platform/content-publishing/` docs; a too-small width is auto-scaled up by Instagram's own servers, but a too-large one was observed in production to fail rather than being scaled down server-side, so this handles the max-width side itself).

Fixed entirely at upload time, in `POST /api/social/upload-instagram-image` (the only place a file becomes `instagram_image_url`), not in the publish flow: after the existing magic-byte/size checks, the buffer goes through `normalizeInstagramImageBuffer` (`lib/social-instagram-image-normalize.ts`) before ever being written to disk. The user's own frame is **never cropped** — an earlier version of this normalizer cropped out-of-range images to fit, which silently discarded part of the photo (wrong UX, reported and replaced). A later version fixed that by letterboxing on flat white, which was itself reported as looking bad (large dead white/black bars) and replaced with a blurred-background version. The current algorithm always keeps the entire original frame and never shows a flat empty bar:
1. **Ratio already valid (4:5–1.91:1)** — the whole frame is kept as-is; only **width** is handled: if it still exceeds **1440px**, the image is proportionally resized down to width 1440 (height scaled by the same factor — never distorted, never cropped). Computed by the pure, unit-tested `computeInstagramFeedResize(width, height)`.
2. **Ratio out of range** — a canvas is sized at the *nearer* valid ratio edge (a too-wide landscape, ratio > 1.91:1, targets **1.91:1**; a too-tall portrait, ratio < 4:5, targets **4:5** — the nearer edge rather than always 4:5 keeps the foreground as large as possible), capped at **1440px** wide. Geometry computed by the pure, unit-tested `computeInstagramFeedContain(width, height)` (`isInstagramFeedRatioAllowed` decides which of the two cases applies; `computeInstagramFeedContain` returns `null` when the ratio is already valid, in which case only step 1 applies). Two independent renders of the *same* source image fill that canvas:
   - **Background** — a clone of the source is scaled+cropped to exactly *cover* the full canvas (`jimp`'s `cover({w,h})`; cropping here is fine, it's decorative, never the frame the viewer is meant to read) then run through a strong box blur (`jimp`'s `blur(r)`, radius ~8% of the canvas's shorter side, capped at 100px) so it reads as an abstract color wash, not a legible duplicate.
   - **Foreground** — the source, proportionally scaled down to fit entirely inside the canvas without cropping or distortion (never upscaled), composited centered on top of the blurred background via `blit({src,x,y})`.

An image that needs neither step (already-valid ratio, width ≤ 1440) has its bytes returned completely unchanged — no re-encode, no quality loss, no behavior change for the common case. Otherwise the result is re-encoded via `jimp`'s JPEG encoder (`quality: 92`) and re-checked against the same 8MB cap the original upload already enforced. Because normalization happens before the file is saved, the same served URL (`GET /api/social/instagram-image/[project]/[filename]`) the post's preview `<img>` and the publish flow both use is always the final, already-normalized file — nothing downstream (preview, `social_posts.instagram_image_url`, `lib/social-instagram.ts`, `social_publications`) needed to change.

`jimp` (pure JS, no native/binary dependency — confirmed via its own `package.json`, unlike e.g. `sharp`) is used only for this: decode buffer → read `width`/`height` → `clone()` → `cover({w,h})` + `blur(r)` for the background → optionally `resize({w,h})` the foreground copy → `blit({src,x,y})` to composite → `getBuffer('image/jpeg')`. `cover()`'s own crop is only ever applied to the decorative background clone, never to the foreground/primary frame. Deliberately not `sharp` or another native-binding library, to avoid adding a platform-specific compiled dependency to the KZ deploy's plain `npm ci && npm run build`.

### Threads autoposting

MVP automated posting for Threads only, via the official Threads Graph API's content-publishing flow — same pattern as Instagram autoposting above (create container → poll → publish), text-only (MVP has no image/video/carousel/replies for Threads). From the post's Publications block, a `threads`-platform publication that isn't already `published` shows a "Publish to Threads" button in place of the manual "Mark as published" button; Telegram/VK/Instagram are unchanged.

`POST /api/social-publications/[id]/publish-threads?project=<slug>` (`lib/social-threads.ts`, project-scoped through `resolveProjectId` like every other route in this module) calls `graph.threads.net/v1.0/{THREADS_USER_ID}/threads` (`media_type=TEXT`, `text`) to create a text media container, a short bounded poll (`GET /v1.0/{container-id}?fields=status,error_message`, up to 10 attempts ~3s apart — Meta recommends ~30s for a text container) waits for `status=FINISHED`, `POST /v1.0/{THREADS_USER_ID}/threads_publish` (`creation_id`) publishes it, then a best-effort `GET /v1.0/{media-id}?fields=permalink` reads back the permalink (unlike Instagram, a failed permalink read here is not fatal — the post has already published by that point). Like Instagram, the target account is **not** resolved from `social_accounts` — a Threads access token is already scoped to one specific user, so the user id and token come from their own env vars, `THREADS_USER_ID` and `THREADS_ACCESS_TOKEN` (server-only, never in Postgres/Git, never sent to the browser; `THREADS_USER_ID` is the numeric Threads user id, never the `@username`). `social_accounts` is still required as a connection guard (a project-scoped, `active`, `platform='threads'` row must exist — linked via the publication's `social_account_id` if set, else the project's first active threads account). `THREADS_API_BASE_URL` is a fourth, non-secret env var (default `https://graph.threads.net`) with the same role as `TELEGRAM_API_BASE_URL`/`VK_API_BASE_URL`/`INSTAGRAM_API_BASE_URL` — `lib/social-threads.ts` appends the `/v1.0` version segment itself, since (unlike `graph.instagram.com`) the Threads Graph API is versioned.

Text sent is `social_posts.threads_text` if non-empty, else `social_posts.body` — same fallback pattern as the other three platforms (`resolveThreadsText`, in `lib/social-threads-text.ts` and unit-tested in `lib/social-threads-text.test.ts` — kept dependency-free, unlike `lib/social-threads.ts` itself, so it's importable by the project's plain node:test runner). Rejected with 400 if longer than Threads' documented 500-character text-post limit.

No schema change: reuses the same `social_publications` columns as Telegram/VK/Instagram, and the `threads_text` column already added by `0005_social_posts.sql`. On success: `status='published'`, `external_post_id` = the published post's media id, `external_url` = its permalink if one could be read back (empty string otherwise), `published_at`, `error` cleared, then `syncPostStatusFromPublications` runs. On any failure — a Threads API error at container creation or publish, the container reporting `status=ERROR`/`EXPIRED`, the bounded poll timing out, or a network failure — the row is set to `status='failed'` with the message in `error`, leaving `external_post_id`/`external_url` untouched; not thrown as an HTTP error, so the route returns 200 with the row and the UI shows it via `publication.error`; calling the endpoint again from `failed` is a normal retry. Calling the endpoint on an already-`published` publication is rejected with 409 before any Threads API call (duplicate-send protection); calling it on a non-`threads` publication is rejected with 400. No scheduler or background job — synchronous, on-demand from the button click only.

### Publish selected channels (fan-out)

A single "Publish selected channels" button in the post's Publications block that replaces having to click Telegram/VK/Instagram/Threads's four individual "Publish to X" buttons one at a time — pure orchestration, no new publish logic: it calls the same four publisher functions above, once each, and reuses their existing per-platform behavior (including each one's own 409 duplicate guard) unchanged.

`POST /api/social-publications/publish-selected?project=<slug>` (body `{ postId }`; `lib/social-publish-selected.ts`, project-scoped through `resolveProjectId`) reads the post's currently-selected `channels` and its `social_publications` rows, then for every selected channel whose row isn't already `published`, calls that platform's existing publisher (`publishSocialPublicationTo{Telegram,Vk,Instagram,Threads}`) — channels already `published` are skipped without any API call. Every call runs independently (`Promise.all` over per-channel calls that each catch their own exceptions) — one channel's platform error, or even a thrown exception, never stops or is reported against another. Instagram's existing "no `instagram_image_url`" pre-flight rejection is not special-cased here; it's the same `{error, status:400}` any other pre-flight failure returns, surfaced as that channel's own failure while the rest of the run continues. The pure result-shaping (mapping a publisher's `{error,status}`/`{row}` result to `published`/`failed`/`already_published`, including treating a 409 hit mid-run — e.g. a concurrent publish between this endpoint's own read and its call — as `already_published` rather than `failed`) lives in `lib/social-publish-selected-outcome.ts`, kept dependency-free so it's unit-tested directly (`lib/social-publish-selected-outcome.test.ts`) the same way `lib/social-threads-text.ts` is.

Response: `{ results: [{ id, platform, outcome: 'published'|'failed'|'already_published', externalUrl, error }, …] }` — one entry per currently-selected channel, in the same shape the UI renders as its "Last run" panel (`components/sections/social-publications.tsx`). The button itself (`shouldShowPublishSelectedButton` in `lib/social-publications-ui.ts`) only shows while the post isn't yet fully published; after a run it refetches `social_publications`/`social_accounts` so every individual channel row (status pill, external URL, retry button) reflects the outcome immediately, same as clicking that channel's own button would. A channel that failed keeps its individual "Publish to X" button for a normal retry — this feature adds no new retry mechanism of its own. No schema change (reuses `social_publications`/`social_posts` as they already are), no queue, no cron, no separate service.

### Social scheduler (auto-publish by publish_date)

Ready posts publish themselves once their `publish_date` arrives, with no one having to open Admin — pure scheduling on top of the fan-out above, not new publish logic: each due post is handed to the exact same `publishSelectedChannels` the "Publish selected channels" button calls.

`publish_date` stayed a plain `TEXT` column — no migration. It always was free-form text (previously written by an `<input type="date">`, `"YYYY-MM-DD"`); the post edit UI now uses `<input type="datetime-local">`, writing `"YYYY-MM-DDTHH:mm"` (no timezone offset) into the same column. Both shapes parse with the native `Date` constructor, though per the ECMA-262 Date Time String Format they're interpreted differently — a date-only string as UTC midnight, a date-time string with no offset as local time in whatever timezone the Node process runs (KZ production's timezone) — an intentional, documented simplification for a single-server MVP rather than pulling in a timezone library. `lib/social-scheduler-due.ts` (`parsePublishDate`, `isPublishDue`) is the one place that logic lives, dependency-free and unit-tested (`lib/social-scheduler-due.test.ts`). The input's display/edit value and the Posts list column both go through `lib/social-publish-date-format.ts` (`toDatetimeLocalInputValue` upgrades a legacy date-only value to midnight so it's still editable in the new control; `formatPublishDate` shows date+time when the stored value carries a time, date-only otherwise), also dependency-free and unit-tested.

`lib/social-scheduler.ts`'s `runSocialScheduler(pool, now?)` is the sweep: finds every `social_posts` row where `status='ready'`, `channels <> ''`, `publish_date <> ''` and `isPublishDue(publish_date)`, and at least one of its `social_publications` rows isn't `'published'` yet (a plain SQL query joined to `projects` for the slug `publishSelectedChannels` needs, then filtered by `isPublishDue` in application code, not SQL, since `publish_date` is text) — then calls `publishSelectedChannels` on each, one at a time (sequential, not parallel, to keep load on the one production server and its DB pool predictable during a catch-up sweep after any downtime). A post with no `publish_date` set at all is never picked up — unchanged, intentional manual-publish behavior for posts that were never given a schedule. One post's unexpected exception (distinct from a single failed channel, which `publishSelectedChannels` already isolates) is caught per-post so it can't stop the sweep over the remaining due posts. Because `publishSelectedChannels` already skips channels that are `published` and defers to each publisher's own 409 guard, and because `syncPostStatusFromPublications` already runs after every publication write, a fully-succeeded sweep leaves the post `status='published'` and a partially-failed one leaves it `'ready'` (not fully published) with its usual failed-channel retry path — both entirely via existing mechanisms, nothing scheduler-specific.

Overlap protection for "two scheduler runs at once" (the one new concern this feature adds — per-channel duplicate protection already existed) is a single Postgres session-level advisory lock (`pg_try_advisory_lock`/`pg_advisory_unlock`, fixed key `727142001`) held for the whole sweep, not per-post or per-project — the simplest mechanism the current Postgres already offers, no new table, no queue, and nothing to clean up if the process dies (the lock releases itself with the DB session). A run that finds the lock already held returns `{skipped: true}` immediately rather than waiting or queuing.

Trigger, chosen over the alternative of a public/authenticated client-facing endpoint or a standalone script: `POST /api/social-scheduler/run` (`app/api/social-scheduler/run/route.ts`) — an ordinary Next.js route (so it can reuse `@/lib/*` the same as every other Social route, unlike a standalone script run via plain `node`, which can't resolve that path alias outside the Next build) called once a minute by a **systemd timer** on the same KZ server via `curl` against `127.0.0.1:3140` — never through nginx or the public domain, so no nginx change was needed. Protected by a shared-secret header (`X-Scheduler-Token`, checked against the server-only env var `SOCIAL_SCHEDULER_TOKEN`) rather than an IP/localhost check, since this app has no trusted-proxy header handling to lean on and nginx wasn't touched to add any — the same shared-secret-header idiom `OLNOO_CRM_API_KEY`/`/api/leads/inbound` already uses. Unset `SOCIAL_SCHEDULER_TOKEN` is a hard 500 refusal, never an open door. Reference unit files and the exact one-time KZ install steps live in `deploy/social-scheduler/` (not wired into `.github/workflows/deploy.yml` — installed once by hand, per that folder's `README.md`); a cron entry would work equally well but wasn't added alongside the timer, to avoid two competing triggers.

## CRM attribution capture, A1 (CRM side only)

CRM preparation for attribution identifiers. **DriveSet is not changed in A1**: the old DriveSet keeps sending leads exactly as before, and the new fields stay empty until DriveSet Capture A2 sends them. Everything is additive and nullable; a missing ClientID / yclid / tracking id **never** blocks a lead.

- **Migration `db/migrations/0015_leads_attribution_ids.sql` — NOT applied by the deploy workflow (it runs no migrations) and NOT yet applied to production.** It must be applied to production **before** the deployment of this code: the INSERT now names the new columns, so deploying first would make every lead insert (inbound, Admin UI, Telegram) fail. It is `ADD COLUMN IF NOT EXISTS` / `CREATE UNIQUE INDEX IF NOT EXISTS`, safe to re-run.
- **New `leads` columns (all nullable):** `lead_tracking_id TEXT`, `metrika_client_id TEXT` (text on purpose: Metrika ClientID is a UInt64 of up to 20 digits and can exceed the JS safe-integer range — it is never converted to a number), `yclid TEXT`, `first_seen_at TIMESTAMPTZ`. **Index:** one partial unique index `leads_lead_tracking_id_uidx ON leads (lead_tracking_id) WHERE lead_tracking_id IS NOT NULL`; no index on `metrika_client_id`/`yclid` (joins read a period-bounded, project-scoped lead set already served by `leads_project_id_idx`; add one when a real lookup exists). Existing columns are reused, not duplicated: `landing_page`, `referrer`, `page_path`, `utm_source/medium/campaign/content/term`. No JSONB.
- **Inbound contract (`POST /api/leads/inbound`):** four new OPTIONAL fields — `lead_tracking_id` (UUID), `metrika_client_id` (string of 1–20 digits; a JSON number is rejected because it may already have lost precision), `yclid` (string, ≤200 chars, no whitespace/control characters), `first_seen_at` (ISO 8601 with a time zone offset, between 2020-01-01 and now+24 h); camelCase aliases are accepted like the utm fields. `null`, `undefined` and `""` mean "not provided" and are not errors. A value that IS provided but malformed returns `400` with a message that never contains the value. Validation: `lib/lead-attribution.ts`; INSERT: `lib/lead-insert.ts`.
- **Idempotency:** a repeated `lead_tracking_id` creates no second lead — the existing lead is returned unchanged (nothing is overwritten) with the same `201` the existing caller requires (DriveSet treats any other status as a failure) plus the header `X-Idempotent-Replay: true`. A tracking id already used by a lead of ANOTHER project returns `409` without any lead data. Concurrent identical submissions yield exactly one lead (unique index). The CRM has no other duplicate fingerprint; the in-memory fingerprint lives in DriveSet's `/api/lead` and hashes the whole body, so DriveSet Capture A2 must keep the new technical fields out of that hash.
- **Compatibility:** old DriveSet (none of the fields) is unaffected; the Admin UI create form and the Telegram Business intake do not send them and are unaffected. A2 note: because a malformed *provided* value is rejected, DriveSet must validate and drop invalid optional attribution values itself instead of forwarding them.
- **Privacy / logging:** the identifiers are not logged, are not echoed in any error text and are not sent to the AI Router. CRM Observer returns them for internal deterministic analytics only — keep them (and `name`, `phone`, `contact`) out of AI prompts.
- **Not in A1:** DriveSet changes, Direct changes (`ADD_METRICA_TAG` untouched), Metrika API, `_ym_uid` / `getClientID`, localStorage, `source` classification, `reachGoal` parameters, Logs API, unified analytics, AI, UI, writes.

## CRM Observer (read-only)

**CRM Observer = read-only.** One GET that returns the leads of ONE project for a period, in a stable shape for the future Direct → Metrika → CRM join. It writes nothing (the route exports only `GET`, the data layer issues one `SELECT` plus the project lookup), does not touch `/api/leads`, the inbound API or the Admin UI, adds no table or migration, and has no AI.

- Endpoint: `GET /api/crm/observer/leads?project=<slug>&from=YYYY-MM-DD&to=YYYY-MM-DD` (`app/api/crm/observer/leads/route.ts`; logic and tests in `lib/crm-observer.ts`, `lib/crm-observer.test.ts`). Access: the external layer in front of admin.olnoo.com only (see "Access to admin.olnoo.com"); no application-level auth.
- **Period:** `from`/`to` are required, strict real calendar dates, inclusive, `from ≤ to`, at most 92 days. They are **Moscow (`Europe/Moscow`) calendar days** — the same day boundaries the Direct Observer uses (Moscow is UTC+3 without DST). The filter is `created_at >= from 00:00 MSK AND created_at < (to + 1 day) 00:00 MSK` on `leads.created_at` (timestamptz); the exact instants are echoed in `period.fromUtc` / `period.toUtcExclusive`. The application timezone is not changed.
- **Project isolation:** `project` is a slug, exactly one value, never `all`; it is resolved through `projects.slug` and the statement filters only on that project's id. Extra query parameters (e.g. `project_id`) are ignored; unknown slug → 404. (The older `GET /api/leads` still returns every project's leads when `project` is missing or `all` — it is the Admin UI's API and was not changed.)
- **Response:** `{ period{from,to,timezone,fromUtc,toUtcExclusive}, project{id,slug,name}, totals{leads}, truncated, leads[] }`, leads ordered by `created_at` then `id`. Each lead: `id, createdAt (ISO UTC), name, phone, status, source, service, contact, landingPage, pagePath, referrer, utmSource, utmMedium, utmCampaign, utmContent, utmTerm` plus (since A1) `leadTrackingId, metrikaClientId (a STRING), yclid, firstSeenAt (ISO UTC)` — all columns that really exist in `leads` (the A1 four are `null` for leads created before attribution capture or when the client did not send them); `""` means "not provided" (stored as empty string), `phone`/`contact` are `null` when absent (`contact` = `tg:<id>` for Telegram Business leads). Not returned: `email`, `company`, `message`, `locale`, `notes`. At most 2000 leads per response: `totals.leads` is the real count and `truncated=true` when the list was cut.
- **Honest limits:** `utm_term` is returned as stored; it is **not** established that it links a lead to a particular Direct search query (that is a separate task after Metrika). DriveSet still marks every site lead `source=Ads`, writes `yclid` only as text inside `message`, and sends no `pageUrl`; there is no lead ↔ Direct campaign/query or lead ↔ Metrika visit link in code.
- **Ads Agent pipeline:** Direct Observer — READY / production confirmed (v0.1 and v0.2) · CRM Observer — READY / production confirmed · Attribution Capture A1 (CRM) and A2 (DriveSet side) — READY / production confirmed · Metrika Observer v0.1 — READY / production confirmed · **Unified Analytics v0.1 — this change (production NOT yet confirmed)** · AI Agent and Writes — only as planned in "Direct Agent — MVP HARD MODE" below (nothing of it is built yet).

## Ads

### Yandex Direct observer (read-only, Ads Agent v0.1, PR1)

Purpose: first real ad data source for the Ads Agent (Observer/Analyst) — own Direct client, no AdCab. **Read-only**: only `campaigns.get`, `adgroups.get`, `keywords.get` and the Reports service are representable (`isReadOnlyDirectMethod`); no add/update/delete/suspend/resume/archive/unarchive exists. No AI, Metrika, scheduler, DB table or UI is attached to it.

- Endpoint: `GET /api/ads/yandex-direct/observer[?days=7][&campaignId=…]` (`days` 1–30, period = last N complete days ending yesterday, Moscow time). `campaignId` may only be an id from `YANDEX_DIRECT_CAMPAIGN_IDS`, otherwise 403; with a single allowed id it can be omitted. Access: external layer only (see "Access to admin.olnoo.com"); no application-level auth.
- Response: `{ period, campaign{id,name,state,status,type,startDate,settings,totals}, daily[], searchQueries[], meta{includeVat,units,requestIds} }`. Money is rubles (Direct micros ÷ 1 000 000, `IncludeVAT=YES`); CPC is computed by our code (spend ÷ clicks), not taken from Direct. `searchQueries` keep Direct's raw `criteria`/`criteriaType` (`---autotargeting` / `AUTOTARGETING`); the deprecated `TargetingCategory` is returned only as an optional raw `targetingCategory` and must not drive logic (if Direct rejects that field the report is re-asked without it).

- Errors: normalised to `kind`, Direct `error_code`, `RequestId` (auth 53 / rights 54 / quota 152 / busy 52,506 retried / request / network / report_timeout / report_format → HTTP 502/502/429/503/502/502/504/502; unknown campaign 404; not configured 503). Source: GitHub **Repository Secrets** with the same names; the existing deploy workflow delivers them on every deploy (see "Env delivery for Yandex Direct" below). Missing/invalid → endpoint answers 503.

Ad groups, keywords, negative keywords and campaign settings arrived in Observer v0.2 (below); ads, sitelinks/extensions and shared negative-keyword set contents are still not read.

#### Yandex Direct Observer v0.2 — campaign structure (read-only)

Scope: **read-only**, **allow-listed campaigns only** (`YANDEX_DIRECT_CAMPAIGN_IDS`). **NO Metrika, NO AI analysis, NO Direct writes, NO DB sync** (nothing is stored; every call reads Direct live). No UI.

- **`campaign.settings`** — always present, from the same single `campaigns.get` (no extra request): `timeZone`, `currency`, `endDate`, `dailyBudget{amount,mode}`, `negativeKeywords[]`, `negativeKeywordSharedSetIds[]`, `counterIds[]` (Metrika counter ids configured in the campaign — ids only, Metrika itself is not read), `strategy{search,network}` each `{type, weeklySpendLimit, bidCeiling, budgetType}` (rubles; the values live in the sibling object named after the strategy type), `options{OPTION: YES/NO}`. Requested for both `TextCampaignFieldNames` and `UnifiedCampaignFieldNames` (Direct returns the matching one). Field names were taken from Direct's own answers (`direct_api_reference`, enum errors) and from a real read of the DriveSet campaign. Note: that read (through AdCab, default API version v5) reported the campaign as `TEXT_CAMPAIGN` with a `TextCampaign` block, while the production Observer (`json/v501`) reports `UNIFIED_CAMPAIGN`; `campaign.settings` is built from either block (`TextCampaign` or `UnifiedCampaign`), so both work.
- **`structure`** — only with `GET …/observer?structure=1` (or `true`; any other value → 400). Opt-in so v0.1 callers keep the same 3 Direct requests: `adGroups[]` (`id, campaignId, name, status, servingStatus, type, regionIds` — ad groups have **no `State`** field in Direct, only `Status` + `ServingStatus`; geo is therefore per ad group, not per campaign), `adGroupsTruncated`, `keywords{items[], truncated}` (`id, adGroupId, campaignId, keyword, isAutotargeting, state, status, servingStatus, bid, contextBid, strategyPriority`, rubles; autotargeting is the pseudo-keyword `---autotargeting` and additionally carries `autotargeting{searchBidIsAuto, categories[], brandOptions[]}`), `negativeKeywords{campaign[], campaignSharedSetIds[], adGroups[{adGroupId, phrases[], sharedSetIds[]}]}` — so an agent can answer "is this phrase already excluded, and where". Minus-words written inside a keyword phrase (`-москва`) stay part of `keyword`; shared negative-keyword **sets** are returned as ids only.
- **Direct methods added (fixed in the client, never taken from the request):** `adgroups.get` and `keywords.get` — both `get` only. Selection is always `CampaignIds: [<allow-listed id>]` (never `Ids`/`AdGroupIds`/`KeywordIds` from outside) and rows of any other campaign are dropped. Mutations (`add`, `update`, `delete`, `suspend`, `resume`, `setAuto*`, …) and every other service stay unrepresentable. Request count with `structure=1`: `campaigns.get` + `adgroups.get` + `keywords.get` (+ the two reports), no per-object calls. Lists are paged (`Page.Limit` 2000, up to 5 pages via `LimitedBy`); beyond that the cap is reported separately: `adGroupsTruncated=true` (ad group list, and with it the ad-group part of `negativeKeywords`, is incomplete) and `keywords.truncated=true` (keyword list only).
- **Failure policy:** if a requested structure read fails the whole request fails with the normalised Direct error (same kinds/HTTP mapping as v0.1) — a negative-keyword check must never be answered from a half-read structure. Without `structure` nothing changes from v0.1.
- Not in v0.2 (next small PRs): ads (`ads.get` — several ad types), sitelinks/extensions, contents of shared negative-keyword sets (`negativekeywordsharedsets.get`), keyword/ad statistics.

### Metrika Observer v0.1 (read-only, Ads Agent)

**Metrika Observer = read-only, aggregated.** One GET with real Metrika numbers of ONE project for a period, so a later layer can put Direct, Metrika and CRM side by side. It writes nothing anywhere (no Metrika write, no Direct write, no DB, no migration, no cron, no AI, no UI) and **does not use the Logs API**.

- Endpoint: `GET /api/metrika/observer?project=<slug>&period=today|yesterday|last7` or `&from=YYYY-MM-DD&to=YYYY-MM-DD` (`app/api/metrika/observer/route.ts`; client `lib/yandex-metrika.ts`, pure part `lib/yandex-metrika-report.ts`, period presets `lib/observer-period.ts`; tests next to them). Access: external layer only (see "Access to admin.olnoo.com"); no application-level auth.
- **Period** (Moscow calendar days, same convention as the CRM Observer; explicit ranges use its strict parser, max 92 days; the Direct and CRM endpoints and their contracts are unchanged): `today` is allowed and answers `period.complete=false` plus a warning `incomplete_period` (numbers are partial); `yesterday` is one complete day; `last7` is the 7 complete days before today; `from/to` may not end in the future and is `complete` only if it ends before today. `period` together with `from/to` → 400.

Source: GitHub repository secret of the same name, delivered by the deploy step (see "Env delivery for Yandex"). Missing/invalid → 503 `not_configured`. The token is sent only in the `Authorization` header, never logged, never returned, stripped from every error.
- **Metrika calls (all GET, fixed in the client):** Management `…/management/v1/counter/113053562/goals` (goal ids, names, exact conditions — only to validate our expectations; failure → warning `goal_list_unavailable`) and Reporting `…/stat/v1/data` ×8 sequential (`accuracy=full`): daily+totals, goals, sources (`lastsignTrafficSource`), UTM (`lastsignUTMSource/Medium/Campaign/Content/Term`), Direct `lastDirectClickOrder` (campaign), `lastDirectClickBanner` (ad), `lastDirectPhraseOrCond`, `lastDirectSearchPhrase`. Breakdown rows: `visits, users, bounceRate, avgVisitDurationSeconds, leadSubmitVisits, leadSubmitReaches` (up to 100 rows, `rows_truncated` warning otherwise). The funnel is `visit → quiz_start → car_selected → package_selected → quiz_phone → lead_submit` counted by **visits that reached the goal**, not by reaches; the steps are not a strict sequence (`funnel_not_monotonic` warning if a later step is larger). Note: `quiz_phone` fires when the contact step opens, not when a phone is typed.

Auth/rights/quota/network/format failures of the main reports stay errors (`auth` 401 / `rights` 403 / `quota` 429 / `request`, `upstream`, `network`, `report_format` → HTTP 502 except quota 429; `not_configured` 503), normalised like the Direct Observer, never with raw bodies.
- **Attribution limits (stated in `meta.limitations`):** Direct → Metrika is **AGGREGATED** (by campaign, ad, phrase/condition, UTM), not per click; Metrika → CRM is **not linked here** (a separate layer); a Direct search phrase is not tied to a CRM lead; `lead_tracking_id` is not a Metrika visit id. Sources/UTM use the last-significant-source model, Direct dimensions the last Direct click.
- **Privacy:** aggregates only. Never returned or requested: name, phone, contact, `metrika_client_id` / ClientID, yclid, visitor identifiers. Search phrases are aggregated Direct queries, like in the Direct Observer.
- **Production status:** **production confirmed** for `today`, `yesterday` and `last7` (visits, users, bounceRate, avgVisitDurationSeconds, goals with reaches and visitsWithGoal, funnel, UTM, Direct campaign/banner/phrase/search phrase; `accuracy=full` works, `sampled=false`, `dataLagSeconds=0`, timezone `Europe/Moscow`). **Direct campaign ↔ Metrika `lastDirectClickOrder.id` is confirmed EXACT by id** (`714796268`).

Known test traffic is excluded from `metrika.excludingTest`, `funnel.excludingTest`, the CRM Direct count and `crm.byStatus`; raw totals (`metrika.visits`, `funnel.*`, `crm.leads`) stay equal to the Metrika/CRM Observers. The `testTraffic` block reports what was found.
- **CRM Direct attribution (`crm.leadsDirect`):** not a known test, `utm_campaign == "714796268"` and `utm_source` in `yandex`/`ya` (normalised). This is the site's first-touch UTM — **AGGREGATED/PROBABLE, not proof of a click**. `crm.leadsUnattributed` = the rest of the non-test leads. No `possibleDuplicates`, no `qualifiedLeads` (the CRM has statuses but no objective quality rule; `crm.byStatus` is a plain split).
- **Response:** `{ project, period{from,to,timezone,complete,preset}, direct{status,complete,campaign{id,name},impressions,clicks,spend,ctr,cpc,includesVat}, metrika{status,visits,users,bounceRate,avgVisitDurationSeconds,sampled,directClickVisits,excludingTest{visits,leadSubmitVisits}}, crm{status,leads,testLeads,leadsDirect,leadsUnattributed,byStatus,truncated}, funnel{scope:'all_visits',quizStartVisits,carSelectedVisits,packageSelectedVisits,quizPhoneVisits,leadSubmitVisits,leadSubmitReaches,excludingTest,direct{scope:'direct_click',…}}, contactIntentVisits{telegram,max,phone,direct{…}}, conversions{basis,clickToVisitPct,visitToQuizPct,quizToContactPct,visitToMetrikaLeadPct,visitToCrmLeadPct,clickToCrmLeadPct,cpl}, daily[{date,impressions,clicks,spend,visits,quizStartVisits,leadSubmitVisits,crmLeads}], breakdowns{campaign,autotargeting,searchQueries,daily}, attribution{directToMetrika,metrikaToCrm,overall,notes}, testTraffic{detected,metrikaVisits,metrikaLeadSubmitVisits,crmLeads,rulesApplied}, warnings[], meta{sources,sampled,generatedAt,sourceDeadlineSeconds,limitations[]} }`. Direct money is RUB **including VAT** (`IncludeVAT=YES`). Every derived metric is `{value, reason?}`; `cpl` also carries `attributionConfidence:'AGGREGATED'`.
- **Formulas:** `clickToVisitPct = Metrika directClickVisits / Direct clicks`; `visitToQuizPct = quizStartVisits / visits`; `quizToContactPct = quizPhoneVisits / quizStartVisits` (`quizPhone` fires when the contact step opens); `visitToMetrikaLeadPct = leadSubmitVisits / visits`; `visitToCrmLeadPct = crm.leadsDirect / directClickVisits`; `clickToCrmLeadPct = crm.leadsDirect / clicks`; all ×100, 2 decimals. All-traffic percentages use the test-excluded values when the test segment was read (`conversions.basis = excluding_test`, otherwise `raw`). **`cpl = direct spend / crm.leadsDirect` only when** the period is complete, Direct and CRM answered, spend > 0, the CRM list is not truncated and `leadsDirect ≥ 1`; otherwise `null` with `period_incomplete` / `direct_unavailable` / `crm_unavailable` / `no_spend` / `crm_truncated` / `no_attributed_leads` — never a fake zero. A zero denominator gives `no_clicks`, `no_visits`, `no_quiz_starts` or `no_direct_visits`. `low_volume` (clicks < 100 or Direct CRM leads < 5) only warns.
- **Breakdowns:** `campaign` EXACT by id; `autotargeting` and `searchQueries` AGGREGATED (the Metrika autotargeting row is recognised by `lastDirectPhraseOrCond` id `11.0` or the exact normalised name `Автотаргетинг`/`Autotargeting`; Direct numbers exact; Metrika visits joined by normalised phrase text; CRM `NOT_SAFE`; top 50 queries by spend); **no query-level CPL**. `daily` merges Direct, Metrika and CRM by Moscow day with zero fill (CRM per day excludes known test leads; Metrika per-day columns are raw).
- **Contact intents** (`telegram`, `max`, `phone` visits with the goal) are separate signals, never summed or counted as leads; a visit may trigger several. They are also given for the Direct-click segment. They are not linked to CRM leads.
- **Failure policy:** each source is `ok` / `partial` / `unavailable` (`meta.sources`); one failing never fails the others; dependent metrics are `null` + reason and a warning is added. HTTP 200 if any source answered; 502 if all failed; 503 if all are unavailable because nothing is configured; 400 invalid project/period; 404 unknown project. Direct and Metrika are cut at a 50 s deadline (`timeout`); the CRM query is awaited as is, never aborted by the deadline. Concurrency makes the latency ≈ the slowest source (Direct reports can poll for readiness). No cache.
- **Attribution (stated in the response):** Direct → Metrika = campaign matched EXACTLY by id, visits AGGREGATED (clicks and visits are different populations); Metrika → CRM = AGGREGATED (first-touch UTM vs last-significant-source); overall AGGREGATED. The funnel is visits that reached each goal, not a proven same-visit sequence.
- **Privacy:** aggregates only; no name, phone, contact, email, ClientID, yclid or lead_tracking_id anywhere in the response (a test injects such values into every source fixture and asserts they never appear).
- **Not in v0.1:** AI, UI, cron, cache, DB, Logs API, ClientID verification, query-level CRM attribution, duplicate detection, `qualifiedLeads`, multi-client onboarding.
- **NEEDS VERIFICATION after production deploy:** Direct Reports accepting `DateTo = today` and its current-day lag; the Direct-scoped goal metrics for all funnel goals; the test-traffic counts; the filter syntax of the test segment (a rejection shows as warning `extras_unavailable`); CRM `yandex/ya` + campaign mapping on the first real advertising lead (the last 7 days had none, so `cpl = null / no_attributed_leads` is expected); latency through admin.olnoo.com.

### Direct Agent — MVP HARD MODE (approved plan; not built yet)

**Goal of the first working scenario:** read search queries → deterministic detector → AI explanation → negative-keyword proposal → human confirmation → manual apply first, Hand v1 later → re-read → verify. The scenario is "found a bad search query → explained → proposed a negative phrase".

**Already exists and is reused (do not rewrite without a concrete blocker):** Direct Observer (read-only client, search queries, keywords, campaign/group negative keywords, campaign/group structure — `?structure=1`), Metrika Observer, CRM Observer, Unified Analytics, REAL/TEST/UNKNOWN classification, MCP summary (`get_driveset_summary`).

**At most 3 PRs:**

1. **Direct MCP Eyes v1.** One compact read-only MCP tool over the existing Direct client (no new client). Whitelist DTO: top search queries by spend; `query`; `criteria` / `criteriaType`; `adGroupId`; impressions; clicks; spend; CPC computed by code; autotargeting marker; current campaign/group negative keywords; and, only where a safe, cheap join already exists, Metrika `leadSubmitVisits` / target visits (AGGREGATED). No CRM personal data, no write, no UI, no new tables. **Before search queries are published through MCP, access to `/api/mcp` must be checked and closed separately** (today nginx opens that exact path with no application auth; its summary DTO deliberately carries no queries).
2. **Negative Query Detector v1.** A pure deterministic function, no LLM inside the calculation. Inputs: Direct spend/clicks, aggregated Metrika target visits / `leadSubmitVisits`, and whether the query is already excluded. Thresholds and protected words (terms of the business that must never become negatives) are set by the owner, not guessed in code. The LLM only explains the detector result and proposes candidate negative keywords. Proposals are first checked on live data; no write actions.
3. **Hand v1** — only if the Detector produced useful proposals the owner agrees with. A separate protected write module / admin route; **no write is added to the read-only Direct client and none goes through the open MCP endpoint.** Campaign-level negative keywords only. Flow: read current negatives → compare with the version used for approval → merge (never replace the list with only the new phrases) → write → re-read → verify → minimal audit log. No generic approval framework. Before building: confirm that the Direct token may write and check Direct's limit on the negative-keyword list size in its API reference.

**Do NOT build before these 3 PRs are done:** Google Ads connector; OAuth onboarding; multi-client abstraction; generic agent framework; RBAC; separate recommendation / approval / action tables; workflow engine; `ads.get`; sitelinks/extensions; bid changes; budget changes; pause/start; CPC, balance or status detectors; post-change analytics framework; universal audit system; separate MCP tools per object when one inspection tool is enough.

**Principle:** any roadmap extension must answer "Without this, does the first useful scenario fail to work?" — if not, do not build it.

**Data limits (do not blur them):**

- Search query → REAL CRM lead is **not provable** today (`utm_term` does not establish the link; Unified has no query-level CPL). Never state "0 REAL leads for this query".
- Use only the AGGREGATED Metrika join where it really exists (Direct search phrase ↔ Metrika `lastDirectSearchPhrase`); a correlation is not attribution.
- Test Traffic must be activated on production (`DRIVESET_TEST_CLASSIFICATION_SINCE` set, see "Test Traffic v1") before REAL/TEST/UNKNOWN is used for product conclusions; until then every non-marker lead is UNKNOWN and CPL is `null`.
- The Direct read client stays strictly read-only.

## Telegram Business intake (implemented, not connected)

Purpose: a client writes to a connected Telegram business account (first target: DriveSet) → one CRM lead; a manager replies in Telegram personally. No auto-replies, no chatbot — no code path calls `sendMessage` or any other chat-writing Bot API method.

- Route: `POST /api/telegram/business-webhook` (`app/api/telegram/business-webhook/route.ts`). Pure update parsing: `lib/telegram-business-update.ts` (unit tests: `lib/telegram-business-update.test.ts`). I/O (owner check, dedup, insert): `lib/telegram-business.ts`. Lead insert reuses `createLeadRecord` (`lib/crm.ts`), which now optionally takes a transaction client.
- Auth: header `X-Telegram-Bot-Api-Secret-Token` compared in constant time to `TELEGRAM_BUSINESS_WEBHOOK_SECRET` (this app has no auth layer, so the secret is the only gate). Wrong secret → 401; config missing → 503.
- Accepted updates: `business_connection` (logged only) and `business_message`. Edits, deletions and any other update type are ignored. Ignored: messages from the owner (manager's own replies), bots, non-private chats.
- Owner allow-list: the message's `business_connection_id` must resolve via the read-only `getBusinessConnection` (cached 10 min) to `TELEGRAM_BUSINESS_OWNER_USER_ID` with `is_enabled=true` — anyone can attach a public bot to their own business account, such connections are inert.
- Lead fields: `project` = `TELEGRAM_BUSINESS_PROJECT`, `name` = Telegram first+last name (else `@username`, else `Telegram <id>`), `contact` = `tg:<telegram_user_id>` (dedup key; numeric id because usernames change), `message` = `Прямое обращение в Telegram (@username, id N).` + first message text/caption (media → `[фото]` etc., ≤2000 chars), `source` = `Direct`, `status` = `New`, email/phone empty. No migration: `leads.contact` from `0010_leads_contact.sql` (must be applied in production before enabling — check with `\d leads`). `contact` is not editable through `PATCH /api/leads/[id]`, so the key stays stable.
- Dedup: in one transaction under `pg_advisory_xact_lock(hashtext('telegram-lead:<project_id>:tg:<id>'))`, an existing lead with that `contact` and status not in `Won`/`Lost` → nothing is created (follow-up messages and Telegram redeliveries); otherwise a new lead. - Errors: transient DB/Bot API failure → 500 so Telegram redelivers (safe because of dedup); logged as `[tg-business]` in journald `olnoo-admin.service`, without message text.
