# OLNOO Monitor — подключение к Content Factory

## Что добавлено

Один короткоживущий Python-компонент с Telethon 1.42.0 вызывается из существующего
scheduler/«Проверить сейчас». Python нужен, поскольку Telethon — Python-библиотека.
Постоянного процесса, второго бота, polling daemon, Redis, SQLite или новой БД нет.
Используется StringSession в отдельном защищённом файле, а не SQLiteSession.
Публикация остаётся внутри существующего OLNOO Social с его атомарным send claim.
Рабочие bot token/Social accounts не меняются.

Это реализация для приёмки, **не проверенное соединение production**. Здесь нет
учётных данных Monitor; коды/2FA и реальные отправки не выполнялись. Telethon
установлен только в локальное временное тестовое окружение для проверки версии
и контрактов методов. Тесты используют фикстуры и mock API, не настоящий аккаунт.

## Установка и авторизация (KZ, только после отдельного разрешения)

Каталог приложения: `/opt/olnoo/projects/olnoo-admin`.

1. Подготовить отдельный обычный пользовательский аккаунт **OLNOO Monitor**.
   Получить его `api_id`/`api_hash` на `https://my.telegram.org/apps`.
   Аккаунт подписывается на публичные username-каналы как обычный пользователь;
   прав администратора источника не требуется. Bot API token сюда не подходит.
2. Через существующий серверный механизм секретов задать **только на сервере**:

   ```dotenv
   TELEGRAM_MONITOR_API_ID=<числовой api_id>
   TELEGRAM_MONITOR_API_HASH=<api_hash>
   TELEGRAM_MONITOR_DIR=/opt/olnoo/secrets/telegram-monitor
   TELEGRAM_MONITOR_PYTHON=/opt/olnoo/secrets/telegram-monitor/venv/bin/python
   ```

   Значения не печатать и не добавлять в Git/Actions/браузер. Определить реального
   пользователя `olnoo-admin.service` командой `systemctl show olnoo-admin -p User`:
   пустой User означает root. **Авторизация и приложение должны читать сессию от
   одного пользователя**. Каталог session — 0700, файл session — 0600, владелец —
   пользователь приложения; никакого chmod 644/777. Родитель должен позволять ему
   пройти к каталогу. Если dotenv недоступен этому пользователю, передать только
   monitor-переменные существующим доверенным механизмом, не ослаблять защиту env.
3. От имени этого пользователя подготовить venv (не системный Python):

   ```bash
   # KZ; разрешённая оператором настройка, в этой работе НЕ выполнялась.
   cd /opt/olnoo/projects/olnoo-admin
   mkdir -p /opt/olnoo/secrets/telegram-monitor
   chmod 700 /opt/olnoo/secrets/telegram-monitor
   python3 -m venv /opt/olnoo/secrets/telegram-monitor/venv
   /opt/olnoo/secrets/telegram-monitor/venv/bin/pip install -r scripts/telegram-monitor/requirements.txt
   ```

4. В интерактивной SSH-сессии с TTY, из папки приложения:

   ```bash
   node --env-file=.env.local scripts/telegram-monitor/auth.mjs
   ```

   Если env уже передан безопасным серверным launcher, использовать тот же
   `node scripts/telegram-monitor/auth.mjs`. Ввести телефон, код из Telegram и,
   если запрошен, облачный пароль 2FA. Ввод невидимый; без TTY команда отказывается
   работать. Не запускать через Actions, pipe или журналирующую команду с кодом
   в аргументах. Команда не печатает session string, API hash, код или пароль.
   Приложение помечено в Telegram как OLNOO Monitor. Файл session является секретом,
   дающим доступ аккаунту: не публиковать, исключить из незащищённых backup/export.
5. Применить **0043, затем 0044** до запуска нового кода через прежний механизм
   PostgreSQL, с `ON_ERROR_STOP=1`. Это не выполнялось на KZ. 0044 добавляет только
   JSONB-метаданные оригинала и расширяет действующие guards для достоверной копии,
   включая медиа без подписи. Файлы/сессия в БД не хранятся. Установленный Social
   guard должен соответствовать контракту 0037; неожиданный guard останавливает
   миграцию вместо замены проверок. Старые migrations повторно не применять.
6. После отдельно разрешённого запуска кода нажать в Sources «Проверить /
   переподключить». Это реальный короткий RPC с текущей сессией, а не проверка
   наличия ключей. Процесс затем завершается: статус означает доступность при
   последней проверке, постоянного соединения нет. При отзыве сессии повторить
   auth-команду; при временном обрыве очередной запуск соединяется заново.
   FloodWait сохраняет время разрешённого повтора, BUSY не создаёт второй процесс.

## Настройка AURELMAR

- Оставить одну активную строку `volodarskiyinvest`; дубли отключить, не удалять.
- «Получение» → **OLNOO Monitor — Telegram Client API**.
- «Копировать оригинал», существующее подтверждение разрешения партнёра на его
  материалы. Отдельных юридических процедур/подтверждений полноты на каждый пост нет.
- «Автоматический», реально подключённый Telegram аккаунт AURELMAR, лимит 3/сутки.
- Существующий `CONTENT_FACTORY_AUTOMATION_ENABLED=true` и защищённый scheduler
  token, первый baseline и timer — по `CONTENT_FACTORY_AUTOMATION.md`, только
  после отдельного разрешения. Не устанавливать второй trigger, если он уже есть.
- Первый Client API poll фиксирует head без скачивания/публикации архива.
  Даже пустой канал имеет достоверный baseline 0. Затем каждый цикл получает новые
  сообщения, сохраняет вложения, обрабатывает очередь в пределах лимита и отправляет
  через Social. HTML — отдельный явно выбранный резерв для ручной обработки;
  ошибки Monitor не подменяются «полной копией» HTML.

## Полнота, хранение и защита

Получается ограниченный snapshot истории после cursor с проверкой head и обеих
сторон границы grouped_id; IDs/даты/UTF-16 entities/подписи каждого сообщения
сохраняются отдельно. Поддерживается signed grouped_id. Последний слишком свежий
альбом (<2 секунд) или изменившийся head не отправляется частично: он остаётся до
следующего цикла. Редкие посты на границе опроса поэтому могут ждать ещё один цикл.
Изменённые/удалённые между опросами исходные сообщения ретроспективно не восстанавливаются.

Исходные файлы без обработки — в прежнем `uploads/content-factory/originals/<project>/<item>/`.
Имена учитывают ID самого Telegram-файла, поэтому новая версия не перезаписывает
старую. Успешные скачивания и SHA-256 остаются при ошибке следующего файла/рестарте.
Checkpoint фиксируется в одной транзакции с материалами и не проходит через
незавершённый пост. Медиа без текста не получают выдуманную подпись.

`original_telegram` — закрытые серверные метаданные MTProto; browser write APIs
не принимают их. Перед отправкой проверяются все файлы, размеры и SHA-256, точный
текст/порядок сообщений и entities. Изменение метаданных сбрасывает approvals.
Для достоверного разрешённого оригинала техническое approval проставляет сервер,
сохраняя прежние DB/account/project guards; для HTML остаётся ручное сравнение.
Перевод MTProto-копии пока блокируется, чтобы не потерять видео/документы или
индивидуальные подписи в старом photo-only translation path. Исходная RU или EN
версия публикуется с тем же содержимым в выбранный канал. Старые HTML/AI переводы
не меняются.
Режим «С согласованием» по-прежнему ждёт одобрения, но не требует сравнивать API
оригинал с HTML. AI-переработка/Quality Gate остаются прежними.

Материал/файлы видны только через существующую Admin-защиту с проверкой проекта;
новый original-media endpoint требует также forwarded Basic header и поддерживает
Range для видео. Сессия никогда не отдаётся через HTTP. Publisher сначала загружает
и проверяет **весь** план; после любого частичного/неопределённого результата Social
остаётся publishing, автоматический повтор запрещён. Уникальный origin claim для
Monitor использует peer + message/group ID, включая переименование username.

## Форматы: реализовано и проверено локально

| Формат | Контракт / ограничения |
|---|---|
| Текст, ссылки, обычное форматирование | Сохраняются entities и UTF-16 offsets, без Markdown/HTML-конвертации |
| Длинный текст | Делится по лимиту 4096; исходный текст восстанавливается конкатенацией, entities смещаются корректно |
| Фото | sendPhoto, до 10 МБ |
| Фотоальбом, фото + MP4 | sendMediaGroup, 2–10; порядок и индивидуальные подписи сохранены |
| MP4 | sendVideo; без перекодирования |
| Документ | sendDocument; исходные байты, имя и MIME; документный альбом только из документов |
| MP3/M4A | Контракт sendAudio предусмотрен; приёмка на реальном Telegram ещё нужна |
| Длинная подпись | Если >1024, медиа и полный текст отдельно; частичная доставка не повторяется |

Cloud Bot API: до 50 МБ на файл (кроме фото), текущая предзагрузка плана до
100 МБ на пост. Более крупные файлы/планы блокируются, не уменьшаются и не
публикуются частично. Превью внешних URL строит сам Telegram, они не скачиваются
как фотографии-вложения. Paid/protected media, голосовые, кружки, стикеры,
некоторые нестандартные entities (например, mention по закрытому user ID),
смешивание документов с фото/видео не заявлены поддержанными. Custom emoji
передаются как entities, но ограничения конкретного bot/account требуют живой
проверки; API-отказ не приводит к публикации упрощённого текста.

**Пока не проверены живым Telegram:** каждый из перечисленных форматов, вход по
коду/2FA, фактическая подписка на `@volodarskiyinvest`, права бота AURELMAR и полный
автоматический E2E. Локальные тесты доказывают преобразования/guards/ошибки и
использование контрактов, но не заменяют такую приёмку.

## Приёмка после разрешённой установки

Сначала тестовый разрешённый канал и обычный пользователь Monitor, без admin.
Проверить baseline (архив не ушёл), затем отдельно текст/entities/ссылки, одно
фото, 4 фото, MP4, фото+MP4, документ, подписи >1024, текст >4096. Для каждого
сравнить исходник, сохранённые байты/SHA-256, порядок и Telegram-результат; зафиксировать
ссылку Social. Повторный sweep и рестарт не должны создавать второй пост. Отдельно
проверить обрыв/FloodWait, partial send, чужой project и суточный лимит. Только после
этой приёмки подтвердить AURELMAR и перевод PR в ready. Merge/deploy/миграций и
изменений сервера в этой работе нет.
